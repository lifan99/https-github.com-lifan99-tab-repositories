# 模块 2｜Python import、对象与配置

预计 14 分钟 · 时间段 10–24 分钟

## 2.1 import 的三个关键动作

首次通常导入一个模块时，Python 查找模块，执行模块顶层代码，再把结果缓存到 sys.modules。import 同时会在当前模块绑定一个名称。后续通常导入会使用缓存，不是每次都重新执行全部顶层代码；显式 reload 或框架执行脚本是另外的机制。

import module 后通过 module.name 访问属性；from module import name 把当时找到的对象绑定到当前模块的名称。理解这种绑定，才能理解后面的 mock 为什么要 patch 被测模块里的名称。[S1]

本项目 from .clients import LLMClient 中的点表示同一包。直接用 python review_system/workflow.py 运行它，容易失去包上下文。应从项目根导入 review_system.workflow，或使用应用入口。

def 创建函数对象并绑定名称，通常不会立即执行函数体；class 创建类对象；调用 Class(...) 创建实例。app.py 的顶层控件是框架入口逻辑，而一般业务模块应尽量避免导入时开始交互或网络请求。

## 2.2 名称、对象、列表与浅复制

赋值通常是在绑定引用，不是自动复制对象。两个名称可以指向同一个列表；list.copy 创建新的外层列表，其中元素仍可能共享。dict.copy 对本题常见的字符串字段足够，但嵌套可变值仍可能共享。

本项目完成结果采用 tuple，响应对象采用 frozen dataclass。它们让外层结构和字段赋值更稳定，但 frozen 并不是对任意嵌套对象做深层冻结。

独立教学示例 E01_objects.py。仅需 Python 标准库，在空目录也可运行。请先读代码，再运行，观察对象身份；不要把它当成项目实现。

```python example=E01_objects.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Response:
    agent: str
    content: str

records = [{"id": "a", "message": "original"}]
alias = records
copied = records.copy()
copied[0]["message"] = "edited"

print("同一外层列表：", alias is records)
print("新的外层列表：", copied is not records)
print("共享内部字典：", copied[0] is records[0])
print("原列表内容：", records)

response = Response("Analyst", "A")
print(response.agent, response.content)
```

@classmethod 的第一个参数是类 cls，不是实例 self。from_env 在读取和校验后通过 cls(...) 生成 Settings。直接 Settings(...) 不会自动运行 from_env 的校验，测试因此可以直接构造固定配置。

api_key 的 repr=False 只让普通配置表示省略凭据，不是加密。客户端仍能访问 settings.api_key。类型注解也不会自动阻止所有错误输入，实际保护来自 if 判断和异常。

预计 12 分钟 · 时间段 24–36 分钟

## 3.1 把“需要一个模型”缩小成“需要一种能力”

工作流不需要知道 token 怎样鉴权、HTTP 怎样解析。它需要的契约是 complete(model=..., messages=...) 返回非空字符串，API 失败时抛 LLMError。

```source

13 |     """A model call failed or returned an unusable response."""
14 |
15 |
16 | class LLMClient(Protocol):
17 |     def complete(self, *, model: str, messages: list[dict[str, str]]) -> str: ...
18 |
19 |
20 | class OpenAICompatibleClient:
```

LLMClient 是结构化接口约定。实现具有相应方法，就可以参与协作，不必继承该 Protocol。当前工作流没有用 isinstance 对客户端做运行时接口检查；Protocol 主要服务于阅读与静态检查。不能把类型标注当成自动校验器。[S3]

依赖注入是把依赖从外部交给使用者：app.py 选择 HTTP 客户端，测试选择假客户端，run_review 接收它们。改变调用对象，不需要改角色顺序。

## 3.2 独立示例：同一函数调用两个实现

独立教学示例 E02_protocol.py。它没有 HTTP，也没有真实项目的三阶段逻辑。

```python example=E02_protocol.py
from typing import Protocol

class Client(Protocol):
    def complete(self, *, model: str, messages: list[dict[str, str]]) -> str: ...

class FixedClient:
    def complete(self, *, model: str, messages: list[dict[str, str]]) -> str:
        return "fixed response"

class EchoClient:
    def complete(self, *, model: str, messages: list[dict[str, str]]) -> str:
        return messages[0]["content"]

def review(text: str, client: Client) -> str:
    return client.complete(
        model="teaching-model",
        messages=[{"role": "user", "content": text}],
    )

print(review("hello", FixedClient()))
print(review("hello", EchoClient()))
```

client.complete 是绑定方法，Python 会传入当前实例作为 self。签名中的 * 要求后续参数使用关键字；所以 complete(model="m", messages=[]) 是契约中的调用方式。

这也提醒你，假的实现可能在类型上满足接口，但内容质量完全不同。接口测试证明可调用，不证明答案正确。

## 3.3 回调也是注入的依赖

run_review 的 on_response 类型是 Callable[[AgentResponse], None] | None。它表示一个消费响应的函数，或不提供函数。工作流把响应交给它，但不使用其返回值。

传函数对象与调用函数不同：on_response=display_response 是传递；display_response(response) 是立即调用。若误写 on_response=display_response(...)，传进去的可能是返回值 None，也可能先触发参数错误。

回调是同步执行的。先保存当前有效结果，再调用回调，是本项目明确的失败恢复选择；到模块 6 会分析其后果。

# 模块 4｜Client API 调用与同步 / 异步

预计 16 分钟 · 时间段 36–52 分钟

## 4.1 把一次请求拆成六部分

OpenAI-compatible 在这里指聊天请求与响应的形态。项目使用 urllib 标准库，没有安装 OpenAI SDK；发往哪个提供商由 Settings.base_url 决定。选择 Qwen 或 DeepSeek 后，三阶段的模型覆盖仍发往同一个端点，并不会自动跨提供商路由。

| 部分 | 当前实现 | 需要理解的边界 |
| --- | --- | --- |
| 地址 | base_url + /chat/completions | 根地址不能重复含完整接口路径 |
| 方法 | POST | 通过请求体发送材料 |
| 鉴权 | Authorization: Bearer key | 只发送到配置的原始请求 |
| 内容类型 | application/json | 请求体是 JSON |
| 请求体 | model、messages、stream=False | 当前未配置其他生成参数 |
| 响应 | choices[0].message.content | 只提取第一份非空文本 |

真实源码节选：clients.py 第 24–39 行。

```source
24 |     def complete(self, *, model: str, messages: list[dict[str, str]]) -> str:
25 |         request = Request(
26 |             f"{self.settings.base_url}/chat/completions",
27 |             data=json.dumps({"model": model, "messages": messages, "stream": False}).encode("utf-8"),
28 |             headers={"Content-Type": "application/json"},
29 |             method="POST",
30 |         )
31 |         # Send credentials only to the configured endpoint, never to redirects.
32 |         request.add_unredirected_header("Authorization", f"Bearer {self.settings.api_key}")
33 |         try:
34 |             with urlopen(request, timeout=self.settings.timeout_seconds) as response:
35 |                 payload = json.load(response)
36 |             content = payload["choices"][0]["message"]["content"]
37 |             if not isinstance(content, str) or not content.strip():
38 |                 raise LLMError("The provider returned empty or non-text content.")
39 |             return content
```

Request 构造请求对象；urlopen 才执行网络操作。with 管理响应资源，退出时关闭。json.dumps 生成字符串，encode("utf-8") 生成字节，json.load 从响应读取并还原 Python 对象。

add_unredirected_header 不把凭据自动复制到重定向请求，但没有禁止所有重定向。它不能保证错误配置的初始端点可信。当前代码选择保留底层异常链，但 UI 只显示经过处理的错误字符串。[S4]

## 4.2 两层 JSON 并非误编码

外层请求是一个 JSON 对象，messages 是列表。内层 user content 必须是字符串，项目把 context 字典编码成 JSON 字符串放在其中。每层服务于不同的接口约定。

独立教学示例 E03_json_request.py。只构造与解析数据，不发网络请求。

```python example=E03_json_request.py
import json
from io import BytesIO

context = {"original_input": "请审查", "analyst_output": "初审"}
messages = [{"role": "user", "content": json.dumps(context, ensure_ascii=False)}]
body = json.dumps({"model": "fake", "messages": messages, "stream": False}).encode("utf-8")

decoded_body = json.loads(body)
decoded_context = json.loads(decoded_body["messages"][0]["content"])
assert decoded_context == context

response = BytesIO(b'{"choices":[{"message":{"content":"OK"}}]}')
payload = json.load(response)
print(decoded_context)
print(payload["choices"][0]["message"]["content"])
```

json.loads 接收字符串或字节；json.load 接收能读取的文件或响应对象。两者最后都返回 Python 对象。

## 4.3 同步、异步、并发、并行、流式是不同轴

| 概念 | 要回答的问题 | 本项目现状 |
| --- | --- | --- |
| 同步调用 | 调用者是否等待结果再往下执行 | 是 |
| 异步 I/O | 等待 I/O 时能否让出执行机会 | 当前客户端不是异步接口 |
| 并发 | 多个任务是否在时间上交错推进 | 三阶段本身不并发 |
| 并行 | 多个计算是否同时在不同执行资源运行 | 当前未为三阶段设计并行计算 |
| 流式输出 | 能否分片读取并展示响应 | 当前 stream=False |

async def 不会自动把 urlopen 变成非阻塞调用。把阻塞 I/O 直接放进协程，仍可能阻塞事件循环。await 也不等于启动多个任务；连续 await A、await B 仍可按顺序等待。[S5]

独立教学示例 E04_async_wait.py。只模拟两个互不依赖的等待，不能当成三角色流程的并发改造。

```python example=E04_async_wait.py
import asyncio
from time import perf_counter

async def wait_for(label: str) -> str:
    await asyncio.sleep(0.02)
    return label

async def main():
    start = perf_counter()
    serial = [await wait_for("X"), await wait_for("Y")]
    serial_seconds = perf_counter() - start

    start = perf_counter()
    concurrent = await asyncio.gather(wait_for("X"), wait_for("Y"))
    concurrent_seconds = perf_counter() - start

    assert serial == concurrent == ["X", "Y"]
    print("顺序等待：", round(serial_seconds, 3))
    print("并发等待：", round(concurrent_seconds, 3))

asyncio.run(main())
```

时间只是教学观察，不做严格性能保证。Critic 需要 A，Judge 需要 A 和 C，所以即便未来采用异步 HTTP，单份材料的三个阶段仍有数据依赖。更自然的并发边界是多个互相独立的审查任务，而不是把当前 A/C/J 直接 gather。

## 5.3 真实工作流逐段精读

真实源码：workflow.py 第 37–74 行。此为原始节选，行号用于对应工程，不是独立运行脚本。

```source
37 | def run_review(
38 |     user_input: str,
39 |     client: LLMClient,

41 |     analyst_model: str,
42 |     critic_model: str,
```

第一段校验：strip 只用于判断是否全空白，没有改写输入。长度检查基于原文 len，包含外侧空白。不要把每日练习题中“先去首尾空白再计算长度”的规则套到这里；那是另一份函数契约。

第二段状态：completed 存 AgentResponse；context 存下一阶段的输入材料。两份状态分别服务结果恢复与模型上下文，不能简单合并为一段字符串。

第三段循环：阶段与模型名配成二元组，for 解包得到 agent、model。每轮创建新的 messages；system 消息来自当前角色，user 消息是当前 context 的序列化。

第四段调用：客户端成功后，工作流再次检查字符串非空。双层检查有理由：将来或测试中的其他客户端也要符合契约，不只是当前 HTTP 实现。

第五段提交：先保存有效响应，再更新 context，再调用回调。这个顺序决定回调出错时当前响应依然存在。只有整个循环完成，函数才返回 ReviewResult。

## 5.4 用 U、A、C、J 追踪状态

| 阶段开始 | 发给模型的上下文键 | completed 中已有回答 |
| --- | --- | --- |
| Analyst | original_input | 无 |
| Critic | original_input、analyst_output | A |
| Judge | original_input、analyst_output、critic_output | A、C |

每轮完成后增加一份响应，再开始下一阶段。Judge 的输出也被加入本地 context，但没有第四次请求，所以它不会被发送给后续角色。

```text
用户输入 U
  └─ Analyst(system_A, {U}) → A
      └─ Critic(system_C, {U, A}) → C
          └─ Judge(system_J, {U, A, C}) → J
              └─ ReviewResult((A, C, J))

完成一阶段：
完整响应 → completed.append → context 更新 → 回调 → 下一阶段
```

## 5.5 什么是循环不变量

循环不变量是在每轮开始时都应成立的性质。它帮助你证明流程正确，而不是只观察一次成功输出。

在第 k 个阶段开始前，k 为 0、1、2：completed 恰好保存前 k 个阶段的有效回答，顺序与阶段顺序一致；context 始终保留原始输入，并包含前 k 个阶段的输出；当前阶段还未调用；任何前序失败都会使代码根本无法进入这一轮。

证明分三步：初始 k=0 时列表为空而 context 有原文；一次成功调用后，追加一份回答并加入对应键，使下一轮满足 k+1；循环终止时 k=3，三个有效回答齐全。失败会抛异常，不适用成功返回结论，而进入部分结果契约。

回调失败发生在本轮提交之后，因此它携带 k+1 份有效回答。模型失败发生在提交之前，因此只携带 k 份回答。不能只说“失败了就丢掉这一轮”，需要区分失败发生的位置。

## 6.1 三层错误边界


## 6.2 失败位置决定保存什么

| 事件 | 尝试模型调用次数 | 保存的有效回答 | 后续调用 |
| --- | --- | --- | --- |
| Analyst 模型失败 | 1 | 无 | 停止 |
| Critic 模型失败 | 2 | Analyst | 停止 |
| Judge 模型失败 | 3 | Analyst、Critic | 停止 |
| Critic 回调失败 | 2 | Analyst、Critic | 停止 |
| 空输入 / 超长输入到工作流 | 0 | 无 | 不开始 |

模型失败与回调失败都转换为 WorkflowError，但语义不同。回调错误使用固定消息，原异常保存在异常链；这避免把任意展示函数的私有细节直接呈现给用户。

普通回调捕获 Exception，不捕获所有 BaseException。KeyboardInterrupt 和 SystemExit 等退出信号可以传播。本项目没有宣称取消时把已完成结果持久化；不要把普通 API 失败恢复扩展成所有异常都保证恢复。

## 6.3 timeout 不等于整个任务的截止时间

urlopen 的 timeout 面向阻塞操作，不是整个三阶段任务的绝对倒计时。当前 60 秒配置不代表整轮一定不超过 180 秒。未来若有任务总期限，需要定义预算、剩余时间和取消机制，而不只是把 timeout 改小。[S4]

项目没有自动重试。再次点击 Review 从 Analyst 重新开始，之前成功阶段可能再次产生请求与费用。设计重试时要先区分限流、账号权限、无效模型、网络断流，并决定重试次数及对用户的影响。

## 7.2 Mock、side_effect 与 patch

Mock 自动记录调用。side_effect 为列表时逐次返回下一项，为异常时抛出该异常。若有效响应后安排一个错误，你可以检查后续调用是否真的停止。

patch 必须替换被测代码查找名称的位置：clients.py 使用 from urllib.request import urlopen，因此应 patch review_system.clients.urlopen。如果只改 urllib.request.urlopen，被测模块已经绑定的原名称未必改变。[S6]

BytesIO 用字节流模拟响应；with patch.dict(os.environ, ..., clear=True) 临时控制进程环境；tmp_path 给测试临时文件目录。三者共同避免真实网络、真实 key 和用户 .env 影响测试。

## 8.1 把页面当作每次重新执行的程序

普通 Streamlit 控件交互会使脚本从头重跑。普通局部变量不承担跨 rerun 保存，st.session_state 存当前连接会话的状态。它不是数据库，不保证浏览器刷新、断开或服务重启后仍保留结果。[S8]

app.py 的 load_project_env 与控件在顶层执行，模型请求只在 st.button 为真的分支中触发。非点击 rerun 进入 else，读取历史回答重新绘制，不发新请求。

真实源码节选：app.py 第 22–53 行。

```source
22 | def display_response(response: AgentResponse) -> None:
23 |     st.subheader(response.agent)
24 |     st.caption(f"Model: {response.model}")
25 |     st.markdown(response.content)
26 |
27 |
28 | if st.button("Review", type="primary"):
29 |     st.session_state.pop("review_result", None)
30 |     st.session_state.pop("review_error", None)
31 |     try:
32 |         settings = Settings.from_env()
33 |         with st.spinner("Reviewing…"):
34 |             result = run_review(
35 |                 user_input, OpenAICompatibleClient(settings),
36 |                 analyst_model=settings.analyst_model,
37 |                 critic_model=settings.critic_model,
38 |                 judge_model=settings.judge_model,
39 |                 on_response=display_response,
40 |             )
41 |         st.session_state.review_result = result.responses
42 |     except WorkflowError as exc:
43 |         st.session_state.review_result = exc.completed
44 |         st.session_state.review_error = str(exc)
45 |         st.error(str(exc))
46 |     except ValueError as exc:
47 |         st.session_state.review_error = str(exc)
48 |         st.error(str(exc))
49 | else:
50 |     for response in st.session_state.get("review_result", ()):
51 |         display_response(response)
52 |     if error := st.session_state.get("review_error"):
53 |         st.error(error)
```

新审查先 pop 旧结果和错误，避免把两轮内容混在一起。工作流正常完成时保存全部响应；失败时保存 exc.completed。配置 / 输入 ValueError 则只显示错误。

这里有两条展示路径：当前审查通过 on_response 逐阶段显示，后续 rerun 根据 session_state 重绘。它们发生在不同执行中，并非同一页面叠加展示。若删掉即时回调，会改变“阶段完成即展示”的体验。

# 模块 9｜harness、AGENTS.md 与 Codex

## 9.1 同一个“Agent”有两种使用场景

开发时，Codex 等工具辅助读文件、修改代码、执行测试。运行应用时，本项目把用户材料交给配置好的聊天模型。这两条链不能混淆：在聊天里让 Codex 改了 AGENTS.md，不代表该文件会被应用发送给 Qwen / DeepSeek。

工程中的 Agent 对象是角色定义。开发工具中的智能体通常还有模型、工具、运行环境、状态与执行循环。对两个概念使用同一个词，容易把本项目误想成一个能自主编辑文件的系统。

## 9.2 harness 的含义与范围

harness 可理解为模型周围的运行支架：组织上下文和调用、执行工具、维护状态、处理生命周期及结果。具体功能由系统决定，不是 Python 的某个固定关键字或类。

OpenAI 官方架构把 harness、执行环境和应用服务器分开说明；其中托管 Codex harness 运行模型 / 工具循环并维护会话。此定义用于解释边界，不表示本项目采用了该托管 API。[S9]

```text
开发侧：用户需求 → Codex 运行支架 → 读文件 / 改代码 / 运行测试 → 验证结果
应用侧：app.py → run_review → client.complete → 模型文本 → 页面
```

当前 workflow 可视作简化业务执行支架的一部分：它组织三个固定阶段、上下文与错误。但它没有自主工具选择、长期记忆或任意规划循环。

# 参考答案｜全部集中在文档末尾

## Q01–Q04：入口、导入与配置

Q01：导入图是 app → config/environment/clients/workflow，workflow → agents/clients，clients → config。调用图是按钮 → 配置 → 客户端实例 → run_review → complete → urlopen → 回调 → 会话保存。import 绑定类对象，不执行 complete；网络请求只有执行到 urlopen 才发生。

Q02：复用 workflow、agents 和客户端接口，终端可以提供自己的打印回调或不提供回调。不要为了使用业务函数而导入具有控件顶层逻辑的 app.py。源码证据是 workflow 不导入 Streamlit，run_review 接收 client 与 on_response。

Q03：from ... import CONFIG 绑定导入时对象。后续给源模块 CONFIG 重新赋另一个对象，不会自动重新绑定导入者的名称。若双方仍指向同一可变对象，并对该对象原地修改，则双方可能看到变化。重新绑定与原地修改是不同操作。

Q04：读取已有进程值 old；override=False 不覆盖。直接 Settings(...) 创建对象，from_env 还执行读取、清理和校验。更改 .env 后可能需要重启并清除 shell 覆盖。

## Q05–Q08：协议、调用与并发

Q05：当前工作流按方法调用协作，没有要求 FakeClient 继承 Protocol，也没有运行时 isinstance 校验。缺少 complete 的对象会在调用位置引发属性错误；不应据此把所有编程错误都伪装成 API 故障。Protocol 可帮助静态检查发现不符合接口的实现。

Q06：传函数对象让工作流在得到响应后调用。带括号是在配置参数时立即执行，可能缺少 response 参数；若执行成功且返回 None，实际传入的是 None，之后不会逐阶段调用它。

Q07：clients.py 的 urlopen 是网络操作位置。外层 JSON 表达 HTTP 请求对象，内层 JSON 是 user content 的字符串，标识原文和前序输出。json.loads 可解开字符串，json.load 从可读响应解码。

Q08：调用 async def 通常得到协程对象，不是字符串。现有工作流的文本验证无法把它当正常响应。Critic 需要 Analyst 返回值、Judge 需要 A 和 C，所以直接并发启动三者无法提供当前所需上下文。多个独立审查任务才可能具有可并发边界。

## Q09–Q12：状态、不变量与异常

Q09：Judge 前 completed 是两个 AgentResponse，内容分别为 A、C；context 有 original_input=U、analyst_output=A、critic_output=C；没有 judge_output。把 completed 说成一个 JSON 字符串会混淆结果对象与请求材料。

Q10：第 k 轮前，completed 恰有前 k 份有效响应且顺序正确，context 保留原文及前 k 份输出。空列表与只有原文建立初值；成功调用后的追加与上下文更新保持性质；正常完成得到三份结果。Critic 回调失败在当前提交之后，快照有两份响应；它不是第三轮已经开始。

Q11：Critic API 失败有一份回答，因为 complete 抛异常时还未 append；Critic 回调失败有两份，因为 append 和 context 更新已经执行。当前代码停止后续请求，未调用 Judge。

Q12：BaseException 还包含退出 / 取消类信号，盲目吞掉可能妨碍终止。Exception 处理普通错误，KeyboardInterrupt 等可继续传播。网络操作超时是局部等待约束；整轮期限是从任务开始到结束的整体预算，需要独立定义和实现，当前没有该总期限。

## Q13–Q16：测试与页面

Q13：会漏掉只调用 Judge、模型名用错、Critic 缺原文、Judge 缺前序回答等问题。可增加调用数为 3、各次模型名正确、三份 context 内容准确、三个 system prompt 不同、回调次数和顺序正确等断言。

Q14：patch adapter.send。adapter 调用的是其模块里已绑定的 send；仅改 transport.send 未必覆盖那个绑定。仍需结合实际导入方式核对，若源码使用 import transport 再 transport.send，则查找位置会不同。

Q15：rerun 重新绘制页面，不是往上次页面永久追加一份。新轮次先 pop 两个旧状态键，本次即时显示；下一次普通执行从新保存结果重放。判断重复问题要在同一执行结果里给证据，不能仅凭两次执行都调用显示函数。

Q16：未点击时不应增加模型请求。当前显示可仍是上一轮结果；因为结果没有保存并展示输入快照，不能据页面上的新输入文字认定旧结果已经对应新材料。这是输入关联的产品改进机会。

```python example=A01_pair_solution.py
from unittest.mock import Mock

def review_pair(text, client):
    if not isinstance(text, str):
        raise TypeError("text must be str")
    if not text.strip():
        raise ValueError("text must not be blank")
    analysis = client.complete(stage="analysis", text=text)
    critique = client.complete(stage="critique", text=analysis)
    return analysis, critique

client = Mock()
client.complete.side_effect = ["A", "C"]
assert review_pair("U", client) == ("A", "C")
assert [call.kwargs for call in client.complete.call_args_list] == [
    {"stage": "analysis", "text": "U"},
    {"stage": "critique", "text": "A"},
]
empty_client = Mock()
try:
    review_pair(" \n", empty_client)
except ValueError:
    empty_client.complete.assert_not_called()
else:
    raise AssertionError("Expected ValueError")
```

## P04 参考提案与课程完成标准

将每轮输入快照与 responses、error 组成同一审查记录。开始新轮次时建立新快照并清空旧状态；成功保存全部响应；普通失败保存本轮快照与 completed。只有编辑输入但未提交时继续显示上一轮快照，避免读者误认为新输入已经审核。

UI 测试至少检查：成功结果绑定本次材料；编辑未提交不增加请求且旧快照仍可辨认；新轮 Critic 失败后保存新快照与一份新 Analyst；后续 rerun 不额外请求。这是一个小范围提案，不需要数据库，也不要求把同步客户端改成异步。

课程完成后，你应能独立解释真实入口、Protocol 协作、JSON 请求、三阶段不变量、部分结果和 rerun。你还应能把“测试通过”“真实连接可用”“模型结论可信”分开报告，并为下一项改进给出明确验收证据。

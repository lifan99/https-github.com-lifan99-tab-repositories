## 起点与今日目标

现有主路径使用 HTTPX 的 `AsyncOpenAICompatibleClient`，工作流内核为 `run_review_async`。同一审核仍按 Analyst → Critic → Judge 执行；多个独立审核可以在同一事件循环等待网络时交替推进。同步 `OpenAICompatibleClient` 留作 HTTP 教学使用。

今天要解释并验证四件事：两份审核上下文不会串；网络、模型、总期限各自如何生效；一份失败或取消不会中断无关审核；取消后任务和名额如何清理并复用。

学习前应能说明 D2 合法报告、非法引用、阶段记录和部分结果规则；未掌握时先补学习，不绕过现有契约。需要保留独立练习时使用 `mvp/.tmp/d3-learning/`，不替换业务内核或修改历史证据。

阅读 [test_async_workflow.py](../tests/test_async_workflow.py) 的 `test_two_reviews_overlap_third_queues_and_contexts_stay_isolated`，对照业务内核。

- [ ] 列出每次调用独立创建的上下文、有效回答、阶段记录与 `ReviewRun`；共享模型客户端不保存当前审核的业务状态。
- [ ] 追踪调用方传入的同一个 `asyncio.Semaphore(2)`，确认一份审核持有名额直至退出。
- [ ] 用已有测试事件解释两份 Analyst 等待区如何重叠，第三份何时进入。
- [ ] 找到原文和前序输出不串入其他审核的断言，而不是仅凭总耗时推断隔离成立。

当前两种容量策略必须区分：直接调用内核、显式共享 `slots` 时可排队；HTTP 服务由 `ReviewService` 管理容量 2，满载立即拒绝，不再让内核重复占名额。runtime 的每次同步调用各建自己的资源，不提供跨调用的全局容量控制。

验收：画出三份审核与两个名额的时间线，并说明异步并发不等于一定节省一半时间。

## T5：验证网络超时、模型期限与审核总期限

当前默认值来自 [config.py](../review_system/config.py)：

| 配置 | 默认值 | 当前含义 | 错误码 |
| --- | --- | --- | --- |
| `REVIEW_TIMEOUT_SECONDS` | 60 秒 | HTTPX connect/read/write/pool 操作超时 | `network_timeout` |
| `REVIEW_MODEL_TIMEOUT_SECONDS` | 60 秒 | 一次 `complete()` 的预算，包括调用内部连接池等待 | `model_timeout` |
| `REVIEW_TOTAL_TIMEOUT_SECONDS` | 150 秒 | 整次审核预算，内核等待传入的名额也计时 | `total_timeout` |

- [ ] 找到有限正数校验和只计算一次总截止时间的位置；服务传入更早截止时间时，内核取更早者。
- [ ] 解释 `asyncio.timeout_at` 与 `scope.expired()` 的用途：不能把任意 `TimeoutError` 都认作本层期限到期。
- [ ] 定位阶段开始前、模型返回后和最终报告发布前的期限检查。
- [ ] 阅读模型预算短、总预算短、第二阶段总期限和排队超时的测试，核对部分结果与错误码。
- [ ] 阅读客户端吞掉计时取消、同步阻塞超预算的测试，解释为什么最后仍不能发布成功报告。
- [ ] 说明总预算临界处的优先级：总期限已到则采用 `total_timeout`；外部取消继续作为取消传播。

验收：排队超时应为 0 次模型调用、三个阶段跳过；总预算不在每个角色开始时重置。期限采用协作式机制，不保证强制打断阻塞代码或在某个毫秒内结束清理。

| 场景 | 必须观察到的行为 |
| --- | --- |
| 正常审核 | A → C → J，D2 报告合法 |
| 两份并发、第三份等待共享名额 | 等待区重叠，峰值不超过 2，上下文分别隔离 |
| 网络、模型、总期限 | 错误码区分，前序有效结果保留，后续阶段跳过 |
| 排队超时或取消 | 模型调用 0 次，不释放未取得的名额 |

| 外层入口退出 | 等待自己创建的任务，随后关闭共享客户端 |

## 1. 角色是配置对象

打开 [agents.py](../../review_system/agents.py)，先读 `Agent`，再读 `ANALYST`、`CRITIC`、`JUDGE` 的提示词。

```python
@dataclass(frozen=True)
class Agent:
    """不可变的角色配置；角色名称用于状态记录，提示词用于模型的 system 消息。"""
    name: str
    system_prompt: str
```

`dataclass` 帮忙生成初始化等方法。`Agent` 对象保存角色名称和系统提示词，`frozen=True` 限制字段被重新赋值。定义这个类、创建三个对象，都没有发送模型请求。

Analyst 的提示词要求做初步分析；Critic 要求对照原文质疑初审；Judge 要求综合判断并返回严格 JSON。共同的 `MODE_GUIDANCE` 说明 `logic`、`evidence` 两种关注方向，以及只使用给定材料的边界。

模型名称不在 `Agent` 中。它由配置传入工作流，所以三个角色可以使用同一个模型，也可以分别配置模型。独立提示词形成角色分工，审核内容是否可靠仍需评估。

**阅读问题：** 删除 `CRITIC` 的定义，会自动变成两角色流程吗？

**对照答案：** 不会。工作流还显式引用 `CRITIC`，角色顺序与结果结构也有相应约束。角色定义和流程调度需要一起理解。

## 2. 一份字典怎样串起三次调用

打开 [workflow.py](../../review_system/workflow.py)，在 `run_review_async` 中依次搜索 `assignments`、`context =`、`messages =`、`context[f`。

初始化节选：

```python
assignments = ((ANALYST, analyst_model), (CRITIC, critic_model), (JUDGE, judge_model))
stages = [StageRecord(agent.name, model) for agent, model in assignments]
completed: list[AgentResponse] = []
context = {"original_input": request.original_input, "review_mode": request.review_mode}
```

`assignments` 固定角色顺序，并把每个角色与模型名配对。`stages` 保存阶段记录，`completed` 保存已经接收的有效回答，`context` 保存下一次模型调用需要的材料。

循环中的消息构造节选：

```python
messages = [
    {"role": "system", "content": agent.system_prompt},
    {"role": "user", "content": json.dumps(context, ensure_ascii=False)},
]
```

`messages` 是列表，里面有两份字典。第一份说明角色职责；第二份把本次审核上下文转成 JSON 字符串。`ensure_ascii=False` 让中文按中文输出。

回答接收部分的节选：

```python
response = AgentResponse(agent.name, model, content)
completed.append(response)
context[f"{agent.name.lower()}_output"] = content
```

`AgentResponse` 保存“谁、使用哪个模型、回答了什么”。`append` 把对象加入列表；最后一行把回答写入上下文字典。运行到 Analyst 时，键名是 `analyst_output`；运行到 Critic 时，键名是 `critic_output`。

| 即将调用的角色 | 此时 `context` 中的键 |
| --- | --- |
| Analyst | `original_input`、`review_mode` |
| Critic | 上述两项，加 `analyst_output` |
| Judge | 上述三项，加 `critic_output` |

每轮都重新执行 `json.dumps`，所以本轮消息包含前面刚写入的回答。三个角色按循环顺序等待，后一个角色不会提前启动。同一函数每次运行都新建这些局部容器。

**阅读问题：** 如果把 `messages` 的构造移到循环外，只做一次，Critic 还能看到 Analyst 的回答吗？

**对照答案：** 不能依靠后续修改 `context` 自动更新。`json.dumps` 已经生成了独立字符串，字典后来新增字段不会改变那段字符串。

## 3. 工作流依赖接口，客户端负责网络

打开 [clients.py](../../review_system/clients.py)，先读 `AsyncLLMClient`，再读 `AsyncOpenAICompatibleClient.complete`。

```python
class AsyncLLMClient(Protocol):
    """异步工作流依赖的最小接口；真实客户端与离线替身均可实现。"""
    async def complete(self, *, model: str, messages: list[dict[str, str]]) -> str: ...
```

工作流需要的能力是：给出模型名和消息，异步得到文本。`*` 后面的参数必须用关键字传入，例如 `complete(model=..., messages=...)`。这里的 `...` 是协议的方法占位，具体行为由传入的客户端实现。

真实客户端中的请求节选：

```python
response = await self.http_client.post(
    f"{self.settings.base_url}/chat/completions",
    json={"model": model, "messages": messages, "stream": False},
    headers={"Authorization": f"Bearer {self.settings.api_key}"},
    timeout=self.settings.timeout_seconds,
    # 禁止跟随重定向，避免将认证信息发送到其他地址。
    follow_redirects=False,
)
response.raise_for_status()
payload = response.json()
content = payload["choices"][0]["message"]["content"]
```

先发送 HTTP 请求，再检查状态码，再解析 JSON，最后取出第一份回答。HTTP 200 仅表示请求成功，不能保证正文一定包含有效回答，所以后续仍检查 `content` 的类型和空白。

该方法把 HTTP、连接、超时或响应格式异常转换为 `LLMError`。其中网络超时使用 `network_timeout` 错误码。工作流据此保存阶段失败状态，无需自己理解供应商的响应结构。

配置来源见 [config.py](../../review_system/config.py) 的 `Settings.from_env`：选择 Qwen 或 DeepSeek，读取对应环境变量，再应用角色模型覆盖值。密钥通过环境配置传入；不要把真实密钥复制到示例或笔记中。

**阅读问题：** `DemoClient` 没有继承 `AsyncLLMClient`，为什么也能传给工作流？

**对照答案：** 它提供了工作流需要的异步 `complete` 方法。`Protocol` 描述接口形状，不要求实现类必须显式继承；类型标注本身也不会代替运行时校验。

## 4. 保留原文，再校验 Judge 的引用

打开 [contracts.py](../../review_system/contracts.py)，选读 `ReviewRequest.__post_init__`、`_finding`、`parse_final_review`。

输入校验只用 `strip()` 判断是否全为空白，不把清理后的文本写回 `original_input`。这是因为报告中的位置必须对应用户提交的原文。

`_finding` 的坐标与引用校验节选：

```python
start, end = value["start"], value["end"]
for field, coordinate in (("start", start), ("end", end)):
    # bool 也是 int 的子类，必须用精确类型比较拒绝布尔坐标。
    if type(coordinate) is not int:
        raise ContractError(f"{path}.{field}: must be an integer, not a boolean.")
if not 0 <= start < end <= len(original_input):
    raise ContractError(f"{path}.start/end: invalid quote range.")
quote = _text(value["quote"], f"{path}.quote")
# 按 Unicode 码点切片核对；不能使用 UTF-8 字节位置，也不能先清理原文。
if original_input[start:end] != quote:
    raise ContractError(f"{path}.quote: must match original_input[start:end].")
```

`start` 包含在引用内，`end` 不包含。例如原文 `"甲乙丙"` 中，`[1:3]` 得到 `"乙丙"`。这里按 Python 字符串的 Unicode 码点定位，不能用 UTF-8 字节偏移代替。

`type(coordinate) is not int` 还处理了一个 Python 细节：`isinstance(True, int)` 为真，而布尔值不应被接受为引用坐标。

`parse_final_review` 继续检查完整报告：字段必须精确匹配，拒绝重复键和非标准数值常量，并检查跨字段关系。例如 `needs_revision` 至少需要一条 finding；`pass` 不能带高严重度问题；`insufficient_evidence` 需要限制说明。

**阅读问题：** 报告通过校验，能否证明模型指出的问题在事实层面正确？

**对照答案：** 只能证明报告满足程序约定，包括引用确实对应原文。判断是否合理、有无漏报，还需要对照材料和人工评价。

## 5. 原始输出、有效回答、最终报告是三层数据

继续读 [workflow.py](../../review_system/workflow.py) 的模型返回处理、`snapshot` 和 `stop`。

输出处理节选，省略了中间保存快照等语句：

```python
if isinstance(content, str):
    stages[index] = replace(stages[index], raw_output=content)
    snapshot("running")
if not isinstance(content, str) or not content.strip():
    raise LLMError("The model returned empty or non-text content.")
if agent is JUDGE:
    final_review = parse_final_review(content, request.original_input)
```

文本先进入阶段的 `raw_output`。Judge 的文本还要通过报告校验，之后才会被加入 `completed`。因此 Judge 返回非法 JSON 时，它的原始文本仍可排查，但有效回答列表只保留 Analyst 和 Critic。

`snapshot` 的核心是重新创建记录：

```python
run.record = ReviewRecord(request, tuple(stages), report, status, error_code)
run.responses = tuple(completed)
```

阶段记录与报告使用冻结数据类，集合用元组保存。`replace` 创建新的阶段对象；新的快照发布后，之前取得的快照不会被后续阶段状态修改。`ReviewRun` 本身是运行句柄，持有的是最近一次快照。

| 情况 | 阶段状态 | 有效回答 | `record.final_review` |
| --- | --- | --- | --- |
| 全部完成 | succeeded / succeeded / succeeded | 三份 | 已校验报告 |
| Critic 模型调用失败 | succeeded / failed / skipped | Analyst | `None` |
| Judge 格式非法 | succeeded / succeeded / failed | Analyst、Critic | `None` |

还有一个顺序需要读清：有效回答先进入快照，再执行 `on_response` 回调，回调完成并通过截止时间检查后，阶段才标为成功。因此回调失败时，可以出现“已有当前回答，但当前阶段失败”的情况。

最终报告只在全部阶段、回调和最后截止时间检查通过后发布。`WorkflowError` 携带失败角色、有效回答和最后记录，便于上层展示部分结果。

**阅读问题：** Critic 失败以后，为什么不让 Judge 用现有材料继续？

**对照答案：** 当前流程约定 Judge 读取原文和前两份回答。程序选择停止后续阶段，以保留明确的失败语义。改变这一行为需要重新设计流程和测试。

## 6. 不联网观察一次完整流程

先读 [fakes.py](../../review_system/fakes.py) 的 `DemoClient.complete`，再读 [workflow.py](../../review_system/workflow.py) 文件末尾的 `run_review`。

`DemoClient` 通过上下文中的键识别当前阶段，返回固定文字与固定报告。它不调用供应商，也不判断材料质量。`run_review` 则通过 `asyncio.run` 调用同一个异步内核，供普通同步脚本使用。

以下是可运行的独立阅读示例：

```bash
.venv/bin/python - <<'PY'
from review_system.fakes import DemoClient
from review_system.workflow import run_review

result = run_review(
    "仅用内存保存记录，重启后历史仍在。",
    DemoClient(),
    analyst_model="demo-a",
    critic_model="demo-c",
    judge_model="demo-j",
)

for response in result.responses:
    print(response.agent, response.model, response.content)
print("运行状态：", result.record.status)
print("报告结论：", result.record.final_review.verdict)
PY
```

预期依次打印 Analyst、Critic、Judge，运行状态为 `succeeded`，报告结论为 `insufficient_evidence`。这两个值并不矛盾：前者表示程序完成流程，后者是演示报告的业务结论。

需要观察每轮上下文时运行现有 [追踪脚本](../../examples/core/E05_project_trace.py)：

```bash
.venv/bin/python examples/core/E05_project_trace.py
```

**阅读问题：** 在一个已经运行的异步函数里应该怎样调用审核？

**对照答案：** 使用 `await run_review_async(...)`。同步入口有 `ensure_sync_context` 检查，防止在运行中的事件循环里嵌套 `asyncio.run`。

## 8. 进阶选读：预算、等待与取消

打开 [workflow.py](../../review_system/workflow.py) 的 `_model_call`、`check_deadline` 和异常处理分支；对照 [test_async_workflow.py](../../tests/test_async_workflow.py)。

固定总截止时间的节选：

```python
deadline = loop.time() + total_timeout_seconds
if total_deadline is not None:
    deadline = min(deadline, total_deadline)
```

`loop.time()` 使用单调时钟，适合计算耗时。截止时间在一次审核中保持不变；切换角色、等到名额后，都不能重新获得一份完整总预算。外部传来的 `total_deadline` 可以进一步缩短预算。

| 预算 | 对应配置字段 | 控制范围 |
| --- | --- | --- |
| 网络操作超时 | `timeout_seconds` | HTTP 客户端的连接、读取等操作等待 |
| 单模型预算 | `model_timeout_seconds` | 一次 `complete` 调用 |
| 整次审核预算 | `total_timeout_seconds` | 排队、三阶段调用、同步回调等总体耗时 |

`asyncio.timeout_at` 用取消机制中断异步等待。同步代码阻塞事件循环时，取消无法立即运行，所以源码在关键位置还显式检查截止时间，拒绝已经过期的结果。

取消处理节选：

```python
except asyncio.CancelledError:
    stop("cancelled", RuntimeError("Review cancelled."))
    raise
```

先保存取消状态，再向上继续传播取消信号。上层才能完成任务清理，而调用方仍可通过运行句柄读取最后快照。

重点测试名称：`test_model_and_total_deadlines_preserve_partial_results`、`test_total_budget_is_not_restarted_after_analyst`、`test_queue_timeout_or_cancel_never_calls_model_or_releases_unowned_slot`。

**阅读问题：** 工作流支持信号量等待，是否说明 HTTP 服务满载后也一定排队？

**对照答案：** 不能这样推断。直接调用工作流时可传入 `slots` 等待名额；HTTP 服务另有准入检查，当前容量满时拒绝新请求。需要继续读服务边界。

## 9. 扩展选读：从页面追到模型

读懂内核后，再按下列顺序追踪完整应用：

```text
app.py                         输入、提交与会话展示
  → api_client.py              访问本地审核 API
    → api.py                   校验 HTTP 输入、调用服务、组装响应
      → service.py             请求准入、任务管理与关闭
        → workflow.py          三角色顺序与审核状态
          → clients.py         访问模型供应商
```

| 源码 | 建议先搜索 | 读这一处的目的 |
| --- | --- | --- |
| [app.py](../../app.py) | `submit_review`、`display_record` | 提交结果如何写入会话，并在页面重跑时展示 |
| [api_client.py](../../review_system/api_client.py) | `ReviewAPIClient.review` | 页面发什么请求、怎样验证返回结构 |
| [api.py](../../review_system/api.py) | `create_app`、内部的 `review` | HTTP 路由怎样把输入交给服务 |
| [service.py](../../review_system/service.py) | `ReviewService.review`、`_execute`、`aclose` | 怎样限制活动审核、执行与清理任务 |
| [api_models.py](../../review_system/api_models.py) | `ReviewBody`、`SuccessResponse`、`FailureResponse` | 对外请求和响应有哪些字段 |

注意两份客户端的目标不同：`api_client.py` 访问本地审核服务，`clients.py` 访问模型供应商。

当前页面等待整次 HTTP 审核完成后展示结果，未提供逐阶段推送。内核的 `on_response` 回调可供直接调用者使用；仅有回调不意味着页面正在实时接收回答。

`api.py` 的 `default_resources` 负责显式选择 `live` 或 `fake`。真实配置错误会阻止启动，不会自动换成演示回答。应用生命周期结束时先关闭服务任务，再退出共享 HTTP 客户端资源上下文。

**阅读问题：** 当前 `request_id` 能否保证服务重启后重发请求不会再次执行？

**对照答案：** 不能。当前只对执行中的重复请求做检查，尚无持久化幂等记录；请求完成或服务重启后不能依靠它避免再次调用模型。

## 1. 为什么一次审核要顺序执行，多次审核却可以并发

先回忆当前依赖：Critic 需要 Analyst 的输出，Judge 需要前两份回答。对同一份材料，同时启动三个角色，会让后两个角色拿不到必需的上下文。

```text
审核 R1：Analyst ─→ Critic ─→ Judge
审核 R2：Analyst ─→ Critic ─→ Judge
         两行之间可以在等待网络时交替推进
```

如果 R1 正等供应商返回，R2 可以发出自己的请求。异步的作用是把等待时间交给其他可推进的任务；它不会消除同一审核内部的依赖，也不会保证模型生成本身变快。

区分两个数字：一次正常审核还是 3 次模型调用；同时运行 2 份审核，整个过程通常产生 6 次调用。并发改变的是这些等待如何交叠。

当前 [clients.py](../../review_system/clients.py) 的主路径通过 await http_client.post 发请求，[workflow.py](../../review_system/workflow.py) 等待当前阶段返回再继续。保留的同步教学类才使用 urlopen；若把它放进 async def 内直接调用，仍会阻塞事件循环。

## 2. async、await 与 Task 分别做什么

`async def` 定义协程函数；调用它会得到协程对象，调用这一动作本身并不完成工作。`await` 等待可等待对象；需要阻塞等待时，任务可以让出执行机会。Task 让协程由事件循环调度。参考 [Python 协程与任务](https://docs.python.org/3.12/library/asyncio-task.html#coroutines)。

下面是业务内核的概念化阅读片段；select_model 与 build_messages 是说明用占位名称，省略契约、期限与状态处理，不能直接执行或替换完整实现：

```python
async def run_review_async(user_input, client):
    context = {"original_input": user_input, "review_mode": "logic"}
    for agent in (ANALYST, CRITIC, JUDGE):
        content = await client.complete(
            model=select_model(agent),
            messages=build_messages(agent, context),
        )
        context[f"{agent.name.lower()}_output"] = content
```

循环里的 `await` 保持本次审核顺序。要同时运行不同审核，需要由入口创建多个任务，而不是把同一份审核的三个角色一起启动。

异步也不等于“执行每一行都会切换任务”。如果当前计算没有真正等待，代码可以连续执行。长时间 CPU 计算、`time.sleep()` 或同步网络调用仍会阻碍其他任务推进。

## 3. 真正异步的客户端需要什么

当前采用 HTTPX `AsyncClient`，工作流通过异步客户端协议调用它。异步请求需要 `await`；客户端应有明确的创建与关闭范围，避免在每次请求的循环中反复创建，才能复用连接。参考 [HTTPX 异步支持](https://www.python-httpx.org/async/)。

```text
最外层异步入口
  创建一个 HTTP AsyncClient
  创建包装它的模型客户端和共享审核名额
    审核 R1 借用客户端
    审核 R2 借用客户端
  等待自己创建的所有审核结束与清理
  关闭 HTTP AsyncClient
```

工作流是借用者：R1 失败不能关闭 R2 仍在使用的客户端。原文、上下文、`completed` 和阶段记录放在每次审核内部；客户端可共享连接设施，但不保存某次审核的可变业务状态。

保持原协议的请求信息：`/chat/completions`、模型名、两条消息、认证头、`stream=False`。响应仍先提取文本，再由工作流执行 Judge 契约校验。异步传输不要求同时引入流式生成。

把旧的同步请求放进线程，可以转移阻塞位置，但取消等待它的协程，不等于已经终止线程里正在执行的请求。本专题验收采用异步 HTTP 调用，线程包装不作为完成证据。

### 如何离线验证

HTTPX 的 mock transport 可接收构造出的请求并返回预置响应，适合检查地址、请求体、错误映射和响应格式。它绕过真实网络，因此不能凭它推断 DNS、TCP 或供应商响应已经验证。参考 [HTTPX transport](https://www.python-httpx.org/advanced/transports/)。

理解异常处理时可对照 [HTTPX 异常分类](https://www.python-httpx.org/exceptions/)，保留当前对外错误信息不包含凭据和供应商原文的行为。异步的成功标准仍包含正确处理错误。

## 4. 三种超时，覆盖三个不同范围

| 范围 | 作用 | 当前错误码 |
| --- | --- | --- |
| 网络操作超时 | 连接、读、写或等连接池的某次操作等待过长 | `network_timeout` |
| 一次模型调用期限 | 单次 `complete()` 整体占用预算过长 | `model_timeout` |
| 整次审核总期限 | 从有效请求进入审核入口起，包含排队与三阶段的预算耗尽 | `total_timeout` |

HTTPX 区分 connect、read、write、pool timeout；这些不是整份业务审核的总预算。参考 [HTTPX 超时说明](https://www.python-httpx.org/advanced/timeouts/)。

例如：一次模型预算 60 秒，审核总预算 150 秒。Analyst 用掉 50 秒、Critic 用掉 50 秒，Judge 开始时只有约 50 秒总预算可用。不能因为“开始了一个新角色”就重新给予 150 秒。

如果审核先排队 30 秒，这 30 秒也要从 150 秒里扣除。模型调用期限从实际调用 `complete()` 时开始，不计等待审核名额的时间；该调用内部等待 HTTP 连接池的时间则计入模型期限。

### 固定截止时间，而不是不断重置倒计时

内核在请求通过校验后计算一次；服务可传入更早的截止时间，内核取更早者：

```python
loop = asyncio.get_running_loop()
deadline = loop.time() + total_seconds
```

`deadline` 交给包住整个审核的 `asyncio.timeout_at`，内层单次调用在 _model_call 中另算截止时间，也使用 asyncio.timeout_at。超时作用域退出时才在外部处理对应 `TimeoutError`，并检查 `expired()` 确认是该作用域到期。参考 [Python 超时接口](https://docs.python.org/3.12/library/asyncio-task.html#timeouts)。

普通业务函数也可能主动抛出 `TimeoutError`。如果不检查来源就一律写成“模型超时”，排错会被误导。模型预算与总预算同时临近时，业务规则应保证总期限已经耗尽就不再发布成功；外部取消则保持取消语义。

### 练习 2：让不同预算分别先耗尽

执行 [E02_timeout_budgets.py](../../examples/async/E02_timeout_budgets.py)：



### 总期限不是硬实时承诺

计时器不能在 Python 正执行一段阻塞同步代码时强制抢占它。现有内核要求校验和回调保持短小，在阶段开始与发布最终结果前再检查截止时间；超时后也可能需要等待清理完成。

因此，“150 秒总预算”表示何时停止继续接受业务工作，不等于“操作系统保证第 150 秒整已经释放所有资源”。不能靠把时间参数写小，解决阻塞代码或吞掉取消的问题。

## 5. 取消不是返回一句“已取消”

任务控制器持有审核 Task，发出取消请求后还要等待它结束。`CancelledError` 继承自 `BaseException`；清理后一般应重新抛出，让外层知道操作确实被取消。参考 [Python 异步异常](https://docs.python.org/3.12/library/asyncio-exceptions.html)。

```python
# 调用方已持有 task；这是控制逻辑片段。
task.cancel()
try:
    await task
except asyncio.CancelledError:
    pass  # 调用方发起了取消，并在这里确认任务已经退出。
```

工作流内部不能捕获取消后伪造成功结果，也不能继续启动 Judge。现有工作流保存有效回答、更新 ReviewRun 快照、退出并传播取消。

`try/finally` 用于清理本次任务拥有的资源；`async with slots` 保证离开已取得名额的作用域时释放名额。不要在尚未取得名额的排队任务里无条件 `release()`，那会把容量错误地增加。

取消是协作式请求。任务已经结束、迟迟不让出控制权或主动吞掉取消，都不是仅调用一次 `cancel()` 就能可靠解决的情况。正常取消依赖协作传播；内核还会在返回后复查期限，阻止吞掉计时取消的客户端发布逾期成功，但不能强制抢占永不让出控制权的代码。

### 超时为什么也会经过取消路径

超时作用域内部也利用取消机制。内层 `await` 收到 `CancelledError` 时，不能立刻把审核最终标成“用户取消”；应先完成清理并向外传播，待期限作用域完成转换后，由工作流外边界确定是总期限、模型期限还是外部取消。

这里的业务设计是：模型期限由单次调用帮助函数转换成模型期限错误；总期限由包住整个审核的作用域识别；仍向外传播的 `CancelledError` 才按外部取消记录。错误码属于工作流解释，不能由模型回答自己填写。

## 6. 谁拥有任务，谁负责等它结束

并发代码需要明确任务所有权：创建任务的入口持有引用，正常时等待结果，异常退出时取消仍未完成的任务，再等待它们清理，最后关闭共享客户端。

不能把任务丢到后台就结束入口。也不能看到某一个任务失败，就直接关闭整个共享客户端，因为另一个审核可能仍然使用它。

`TaskGroup` 默认会在一个子任务出现普通异常时取消其他任务；`gather` 的默认异常行为不同。独立审核需要明确隔离策略，例如各自捕获预期业务错误，或收集 `gather(..., return_exceptions=True)` 的每项结果并逐项区分成功、失败与取消。参考 [Python 任务组](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)及[并发等待](https://docs.python.org/3.12/library/asyncio-task.html#running-tasks-concurrently)。

`return_exceptions=True` 不是把异常视为业务成功。本专题脚本只在收拢清理结果时使用它；业务实现必须检查每项结果。

### 审核名额与连接池不是同一个限制

直接调用内核时，可由调用方传入同一个共享 Semaphore(2) 包住各次审核。第三份审核等名额，并在等待期间受总预算约束。信号量适用于同一事件循环内的协作任务，不是跨线程或跨进程的全局限流器。参考 [Python 异步信号量](https://docs.python.org/3.12/library/asyncio-sync.html#semaphore)。

HTTP 连接池限制的是连接资源，不能直接当成“同时两份审核”的业务限制。每份审核如果自己新建一个 `Semaphore(2)`，也不能约束整体并发数。

## 7. 如何承接审核的状态契约

现有契约在有效回答、原始输出和最终报告之外，已包含以下异步状态：

| 位置 | 现有字段与取值 | 目的 |
| --- | --- | --- |
| `ReviewRecord.status` | `queued / running / succeeded / failed / cancelled` | 表达整份审核处于排队、执行还是结束 |
| `ReviewRecord.error_code` | 原有业务错误码，加上 `network_timeout / model_timeout / total_timeout / cancelled`；无错误为 `None` | 排队失败时也能说明原因 |
| `StageRecord.status` | 增加 `cancelled` | 区分外部取消与普通阶段失败 |
| `StageRecord.error_code` | 对已启动阶段记录相应错误 | 保持阶段定位 |

调用方为每份审核创建独立 ReviewRun 并传给内核。它持有最新不可变 record 与 responses 快照；取消后可读取，但已取消 Task 不会返回成功 ReviewResult。ReviewRun 只能使用一次，不能让两份审核共享。

状态例子：

| 情况 | 审核级状态与原因 | A / C / J | 最终报告 |
| --- | --- | --- | --- |
| 正常完成 | succeeded | succeeded / succeeded / succeeded | 已验证报告 |
| Critic 模型期限到达 | failed，model_timeout | succeeded / failed / skipped | `None` |
| Critic 等待时总期限到达 | failed，total_timeout | succeeded / failed / skipped | `None` |
| Critic 等待时外部取消 | cancelled，cancelled | succeeded / cancelled / skipped | `None` |
| 排队时总期限到达 | failed，total_timeout | skipped / skipped / skipped | `None` |
| 排队时外部取消 | cancelled，cancelled | skipped / skipped / skipped | `None` |

阶段之间停止时，没有正在运行的阶段，不要伪造一个“已调用却失败”的角色；已完成阶段保留，待执行阶段记为 skipped。`completed` 继续保存通过本阶段输出校验的回答，回调失败时保留当前回答的 已有规则不变。

Judge 的字段校验不通过仍是 `invalid_output`；展示回调抛普通异常仍是 `callback_error`。异步迁移不应把所有异常都变成“超时”。

## 8. 同步脚本与当前 Streamlit 入口怎样接入

业务实现只有 run_review_async。同步 Python 脚本可使用 run_review 薄封装；runtime.run_review_with_settings 则负责单次调用的事件循环、HTTP 客户端创建与关闭。调用者传入的客户端仍必须实现异步 complete。

`asyncio.run()` 不能在同一线程已经运行事件循环时再次调用；异步测试或未来异步服务应直接 `await` 工作流。参考 [Python Runner](https://docs.python.org/3.12/library/asyncio-runner.html#running-an-asyncio-program)。

不要将一个异步客户端缓存到页面会话，再让不同按钮点击创建的新循环反复使用它。多审核共享客户端的验证，应在一个外层异步入口和同一个循环内完成。

当前页面通过 api_client 的同步 HTTP 客户端请求本地 FastAPI，由服务生命周期共享异步模型客户端并统一管理容量。页面在整次请求返回后展示，没有停止按钮或逐阶段推送。HTTP 服务满载立即拒绝，直接内核调用的 slots 排队策略仅用于对应调用方。

## 9. 怎样写出有说服力的异步测试

纯粹检查“函数是 async”不能证明它没有阻塞。只断言耗时小于某个很紧的阈值，也容易因机器负载产生不稳定结果。

优先使用事件建立可观察顺序：A 已进入等待、B 也已进入、取消已发出、清理已完成、下一份任务取得名额。时间限制用于防止测试死锁，阈值留余量；业务结果靠状态、次数、内容和事件断言。

| 测试问题 | 有意义的断言 |
| --- | --- |
| 并发是否发生？ | 第二份审核能在第一份等待时进入自己的模型调用 |
| 上下文是否串了？ | 每次消息只含对应原文和该审核前序输出 |
| 总期限是否重置？ | 同一个截止时间覆盖前两阶段和排队，后续阶段不能获得全新预算 |
| 是否真的取消？ | 等待目标 Task 得到取消；无 Judge 调用；清理事件触发 |
| 是否泄漏名额？ | 结束后同一信号量可再次获取；排队取消不增加名额 |
| 另一份审核是否被误伤？ | 目标失败后，另一份仍得到自己的合法报告 |
| 客户端是否误关？ | 取消一份审核后，其他审核仍能用它；入口结束后再确认关闭 |

业务测试可在普通 pytest 函数里写一个 `async def scenario()`，最后 `asyncio.run(scenario())`。测试内的事件、信号量、客户端创建与关闭应在这个 scenario 内完成。每个测试自己的循环与资源一起结束，避免跨循环共享对象。

现有 [test_workflow.py](../../tests/test_workflow.py) 保留顺序、上下文、失败停止与回调规则；test_async_workflow.py 验证并发、期限和取消，test_runtime.py 验证资源生命周期。概念脚本的断言不能替代业务回归。

运行实际业务内核集成演示：

```bash
PYTHONPATH=. .venv/bin/python examples/async/E04_integrated_reviews.py
.venv/bin/python -m pytest -q tests/test_async_workflow.py tests/test_async_clients.py tests/test_runtime.py
```

E04 依次验证并发隔离、总期限、主动取消及取消后复用；模型仍为 fake。

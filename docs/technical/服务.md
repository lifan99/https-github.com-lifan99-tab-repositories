先从 [阶段路线](../../study/学习路线.md) 确认本次任务；首次学习无需阅读全文。现有行为以源码与测试为准，历史工程证据见 [实施总览](工程状态.md)。

## 1. 增加服务边界后，谁负责什么

```text
调用方（Streamlit、测试、curl）
                 ↓ HTTP / JSON
FastAPI 路由：请求校验、状态码、响应序列化
                 ↓ await
ReviewService：准入、审核标识、任务生命周期
                 ↓ await
异步工作流：A → C → J、上下文、契约校验、期限与部分结果
                 ↓ await
异步模型客户端：HTTP 请求、供应商响应与网络错误
```

客户端层只关心怎样访问模型；工作流关心三个角色怎样协作；Service 关心多份审核怎样被接纳、跟踪和结束；路由关心怎样用 HTTP 表达这些结果。

例如供应商连接失败：客户端产生模型调用错误，工作流附上失败阶段及部分结果，Service 完成本次清理，路由把结果翻译成 502。没必要让工作流导入 FastAPI 的 `HTTPException`。

“服务使用异步”描述服务器如何调度等待；“POST 一直等到完成再返回”描述调用协议。它们可以同时成立。本专题不返回 202 后让用户轮询，不提供历史查询或取消端点。

## 2. 先约定两个端点

### GET /healthz

成功响应为 200，例如：

```json
{"status": "ok", "execution_mode": "fake"}
```

它表示应用已启动并能处理这个轻量请求，不会调用模型。HTTP 服务存活不证明供应商账号可用，更不证明审核结论准确。

`execution_mode` 是服务配置的 `fake` 或 `live`；`review_mode` 则是一次审核关注 `logic` 还是 `evidence`。两个 mode 含义不同。

### POST /api/v1/reviews

请求示例：

```json
{
  "request_id": "day4-demo-001",
  "original_input": "仅用内存保存记录，重启后历史仍在。",
  "review_mode": "logic"
}
```

| 字段 | 规则 | 谁决定 |
| --- | --- | --- |
| `request_id` | 必填字符串，1–64 个 ASCII 字母、数字、下划线或连字符 | 调用方，用于识别执行中的重复提交 |
| `original_input` | 必填字符串，非空白，最多 20,000 字符，保留原文 | 调用方 |
| `review_mode` | `logic` 或 `evidence`，省略时默认 `logic` | 调用方 |
| `review_id` | 接受审核后由服务生成的唯一标识，当前使用 UUID 字符串 | 服务端，不是请求字段 |

其他请求字段拒绝。API Key、供应商地址、模型配置和执行模式由服务环境配置，不能由这份审核请求替换。

请求里的 `request_id` 和响应里的 `review_id` 不互相替代。前者是调用方表达的提交标识；后者标识服务实际接受的一次运行。同一请求标识以后被重新接受，会生成新的审核标识。

## 3. HTTP 校验与 契约校验如何配合

FastAPI 的请求模型可以校验 HTTP 输入的字段与类型。数据契约仍承担业务规则和模型输出校验；绕过 HTTP 直接调用工作流，也必须得到一致的拒绝行为。

Pydantic 默认可能进行类型转换。这里采用 v2 严格模式、禁止多余字段，并用字段校验器检查空白与标识；校验函数返回原值，避免改变 原文引用坐标。参考 [Pydantic 严格模式](https://docs.pydantic.dev/latest/concepts/strict_mode/)与[字段校验器](https://docs.pydantic.dev/latest/concepts/validators/)。

下面直接使用现有请求模型。安装项目依赖后，在项目根目录执行：

```bash
.venv/bin/python - <<'PYCODE'
from pydantic import ValidationError
from review_system.api_models import ReviewBody

body = {"request_id": "reading-d4", "original_input": "请审查这段方案。"}
request = ReviewBody(**body)
assert request.review_mode == "logic"
assert request.original_input == body["original_input"]
for change in ({"original_input": " "}, {"request_id": "bad id"}, {"api_key": "synthetic"}):
    try:
        ReviewBody(**{**body, **change})
    except ValidationError:
        print("非法请求已拒绝")
    else:
        raise AssertionError("应拒绝非法请求")
PYCODE
```

这验证真实请求模型，但没有经过路由，也不调用模型。不要把其通过等同于 HTTP 接口验收。

现有 api_models.py 复用 contracts.py 的输入长度常量和规则，避免 HTTP 层允许 20,000 字符、业务层却只允许 10,000 的漂移。框架响应校验也不能代替 Judge 摘录与原文一致性的检查。

请求校验异常可能包含输入与内部上下文。当前通过自定义 `RequestValidationError` 处理器返回统一、有限的错误信息，不把原始材料完整回显到错误正文。参考 [FastAPI 错误处理](https://fastapi.tiangolo.com/tutorial/handling-errors/)。

## 4. 成功与失败使用同一组顶层字段

当前响应信封如下：

| 字段 | 成功时 | 失败或拒绝时 |
| --- | --- | --- |
| `request_id` | 已验证的调用方标识 | 422 时为 `null`；其他情况返回已验证标识 |
| `review_id` | 接受时生成的标识 | 准入前拒绝为 `null`，已接受后失败保留标识 |
| `execution_mode` | `fake` 或 `live` | 同样返回服务模式 |
| `status` | `succeeded` | 准入前 `rejected`；运行后 `failed` |
| `responses` | A、C、J 的有效回答 | 本次已通过阶段输出校验的回答；准入前为空列表 |
| `stages` | 三阶段公开状态 | 普通工作流失败保留三阶段；准入拒绝为空；内部 500 可能无完整记录 |
| `final_review` | 已通过 契约校验的结构化报告 | 必须为 `null` |
| `error` | `null` | `code`、安全 `message`、`stage`；无阶段时 `stage=null` |

`responses` 每项仍含 `agent`、`model`、`content`。公开的 `stages` 每项含 `agent`、`model`、`status`、`error_code`、`raw_output`，未取得文本时 `raw_output=null`。

`raw_output` 指模型成功返回的回答文本，也可保存契约失败的 Judge 原文；它不同于 HTTP 错误响应里供应商的原始正文。失败的模型回答可以供后续 UI 标注展示，供应商错误正文和内部异常堆栈不出现在这个字段里。

工作流的运行记录可能还有原始请求、内部异常等内容，API 应按公开字段显式构造响应，不能直接把整个运行对象转字典返回。使用响应模型可以限制与检查输出字段；错误处理器直接返回 `JSONResponse` 时，也要先用错误 DTO 验证，不能只依赖 OpenAPI 中写了一个 schema。参考 [FastAPI 响应模型](https://fastapi.tiangolo.com/tutorial/response-model/)。

例如，执行中的重复请求返回 409：

```json
{
  "request_id": "day4-demo-001",
  "review_id": null,
  "execution_mode": "fake",
  "status": "rejected",
  "responses": [],
  "stages": [],
  "final_review": null,
  "error": {
    "code": "duplicate_request",
    "message": "相同请求标识的审核仍在执行。",
    "stage": null
  }
}
```

这次拒绝不创建新的审核，也不返回正在运行的另一份审核结果。

### 201 与 Judge 的 verdict 不同

201 表示这次审核执行完成、报告合法。Judge 可以认为方案需要修改，甚至认为证据不足；这依旧是成功完成的一次审核。

只有系统不能提供符合约定的结果，例如超时、调用失败、Judge 输出无法通过契约校验，才进入失败响应。报告不赞成用户方案，不是 HTTP 错误。

201 也不表示已经把报告存入数据库。本版直接返回创建的报告表示，不提供结果查询地址，不承诺断线重连后能找回报告。

## 5. 状态码告诉调用方应该怎样理解问题

下表是针对本项目的映射选择，HTTP 状态之外仍保留细分错误码。

| HTTP | 情况 | 错误码 | 是否已执行模型 |
| --- | --- | --- | --- |
| 201 | 审核成功完成 | 无 | 正常 3 次 |
| 422 | 请求 JSON 或字段不符合约定 | `invalid_request` | 否 |
| 409 | 相同 request_id 的审核仍在执行 | `duplicate_request` | 这次提交没有 |
| 429 | 本地服务同时审核数达到上限 | `capacity_exceeded` | 这次提交没有 |
| 502 | 供应商调用失败，或模型报告不合格 | `model_error` / `invalid_output` | 可能已有部分调用 |
| 504 | 网络操作、模型调用或总预算超时 | `network_timeout` / `model_timeout` / `total_timeout` | 取决于超时位置 |
| 500 | 内部代码或响应模型缺陷 | `internal_error` | 取决于失败位置 |
| 503 | 服务关闭阶段停止准入 | `service_unavailable` | 这次提交没有 |

几个易混点：

- 用户给错字段是 422；用户请求正确、Judge 给错字段是 502/invalid_output。
- 供应商的 429 在此归入 502/model_error，不直接透传为本地容量满载。
- live Key 缺失是服务启动配置问题，不能冒充用户提交材料有误。
- 取消应继续传播。连接已经断开时，通常无法再承诺客户端会收到一份 504 或其他正文。

框架自己的未知路径、方法不支持等 404/405 不在这个审核业务映射表中，保留框架行为。

## 6. 容量限制和重复请求保护是一件事吗

它们回答不同的问题：409 表示“这份请求标识正在执行”，429 表示“新的请求暂时没有名额”。

现有 ReviewService 维护活动标识集合，容量固定为 2。一次准入按顺序完成：

```text
服务正在关闭？          → 503
request_id 已在活动集合？→ 409
活动数量已经达到 2？    → 429
否则：登记标识并占用名额 → 创建审核记录并执行
```

在单事件循环中，把检查和登记写成没有 `await` 的短同步步骤，可以避免其他协程在中间插入。它只适用于所有访问都在同一循环的前提；不能推广为线程安全或多 worker 的全局限制。

审核退出时，在 `finally` 中删除本次标识。准入失败的请求没有取得名额，不应执行“释放”。取消发生在任务真正开始之前，也不能留下预先登记却无法清理的占用。

### 与 异步内核的排队策略有何变化

异步示例用信号量让第三份审核排队；本地 HTTP 入口选择容量满立即返回 429。它们是调用入口的不同政策，异步内核的角色顺序和错误规则不变。

HTTP 容量只由 ReviewService 管理一次；不要服务先占一个名额，内核又等待同一个名额。需要排队的离线批处理，仍可在自己的调用入口使用 异步内核的信号量。

### 执行中去重不等于持久化幂等

假设第一次请求已经完成，但成功响应在传输中丢失。活动标识已清除，此时重新提交同一个 `request_id`，本设计会再次调用模型。

所以它只防止重叠执行的重复提交，不保证“同一请求永远只计费一次”。本专题没有结果缓存、数据库或跨重启记录；不能把 409 规则包装成持久化幂等承诺。

## 7. 把资源生命周期交给应用

每来一个请求就创建并关闭整个共享客户端，会失去连接复用；某个请求失败就关闭共享客户端，还会影响另一份审核。服务把这些资源交给应用生命周期管理。

FastAPI 的 lifespan 使用异步上下文管理器组织启动与关闭：`yield` 前准备资源，`yield` 后清理。参考 [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/)。

现有应用的资源顺序：

```text
启动：加载配置 → 创建客户端 → 创建 ReviewService → 开始接收请求
运行：多个路由调用同一个服务；每份审核有独立记录
关闭：停止准入 → 取消并等待仍在运行的审核 → 关闭共享客户端
```

`create_app()` 返回新应用，便于测试注入 fake 工厂。导入模块不应自动读真实配置或发网络请求。fake 模式无需 Key；live 模式配置错误时应明确启动失败，不能默默返回 fake 结果。

Service 如创建审核子任务，就持有并收拢这些任务：子任务开始后才准入，取得名额后立即进入 `try/finally`；父处理任务取消时也要等待子任务退出。这样取消发生在子任务尚未运行时不会泄漏名额。

启动一个 worker 是当前设计前提。两个 worker 各有一个容量为 2 的服务实例，就可能合计接受 4 份审核，也无法靠各自的活动集合识别对方正在执行的请求。

## 8. 期限和客户端断开属于哪一层

内核已经给审核定义总截止时间。Service 在有效请求进入 Service 时建立它，再把同一个截止时间传给工作流；路由、Service 和每个角色不能各自重启一个完整预算。

本专题 API 不排队，满载直接拒绝；总预算覆盖被接受后的业务执行和校验，不覆盖客户端上传请求和响应在网络上的全部传输时间。当前 UI 的 REVIEW_API_TIMEOUT_SECONDS 默认取声明的总预算加 30 秒，配置时必须大于该总预算；前后端分开配置时仍需人工协调，并给清理与传输留出余量。

客户端等不及返回，并不证明服务器已经停止审核。服务器处理任务被取消时，应沿 异步内核的路径取消、清理并传播；但实际 TCP 断开是否会导致 handler 取消，需要专门验证，不能只凭“用了 FastAPI”作保证。

本服务不增加取消端点或断线恢复查询。已断开的客户端可能拿不到部分结果，服务里的内存记录也不承诺长久保存。状态 499 也不作为本项目的对外协议。

## 9. 如何测到真正的接口边界

只调用 `service.review()` 的测试能验证服务行为，但没有经过 HTTP JSON 解析、路由、响应序列化或状态码转换。接口测试必须进入真实应用路由。

FastAPI `TestClient` 适合普通测试；用 `with TestClient(app)` 才能按上下文管理方式运行 lifespan。参考 [FastAPI 测试生命周期](https://fastapi.tiangolo.com/advanced/testing-events/)。

并发请求测试可用 HTTPX `AsyncClient` 与 `ASGITransport`，让请求在进程内进入应用。ASGI transport 本身不启动应用生命周期；测试需要显式管理 lifespan，并保证客户端、服务资源和请求位于同一个事件循环。参考 [FastAPI 异步测试](https://fastapi.tiangolo.com/advanced/async-tests/)与 [HTTPX ASGI transport](https://www.python-httpx.org/advanced/transports/)。

两种测试各自创建应用和资源，避免先在 TestClient 的线程启动对象，再交给另一个循环使用。要检查已处理的 500 正文时，还应配置测试客户端不把服务器异常直接重新抛给测试调用方，同时保留单独验证内部异常的测试。

### 每个断言都对应一个行为

| 问题 | 应检查的内容 |
| --- | --- |
| 请求是否被正确拒绝？ | 422，统一正文，模型调用 0 次 |
| 报告是否真有效？ | 201、三阶段回答、结构化报告字段，不只检查“有 JSON” |
| 409/429 是否真的阻止调用？ | 让已有请求停在事件上，再提交新请求，检查调用次数没有增加 |
| 超时是否保留前序输出？ | 504 与准确错误码、部分回答、最终报告为空 |
| 模型失败是否误伤其他请求？ | 另一份审核仍取得自己的合法报告 |
| 清理是否结束？ | Task 完成、活动集合为空、新请求可接受、客户端在正确时机关闭 |
| 是否读了真实凭据或联网？ | 测试注入 fake 工厂，替换环境加载，不依赖真实 Key |

OpenAPI 的响应声明描述契约，不等于测试已经验证过。ASGI 进程内测试通过，也不等于本机监听、端口、真实网络和供应商链路均通过。本机 fake 演示使用 E03；live 验证单独记录。

```bash
.venv/bin/python -m pytest -q tests/test_service.py tests/test_api.py tests/test_api_client.py
PYTHONPATH=. .venv/bin/python examples/api/E03_local_http_smoke.py
```

E03 需允许回环监听，自动验证 201、422、504 后关闭；完整手动启动与 curl 命令见HTTP 服务专题练习。

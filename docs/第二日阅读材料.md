# 第二日阅读材料：从一段回答到可校验的审核报告

初版：2026-10-14；修订：2026-10-16。配套任务：[第二日计划任务](第二日计划任务.md)。建议阅读 45 分钟，练习另用 20–30 分钟。

本文讲解现有 [contracts.py](../review_system/contracts.py) 与工作流的契约边界。历史实现过程见 [D2 实施记录](day-02-evidence.md)，当前整体状态见 [实施总览](implementation-status.md)。

第一天我们追踪了“原文 → Analyst → Critic → Judge”。第二天研究这个问题：Judge 给出一段看起来完整的文字，程序凭什么认定审核已经成功？

先理解文本检查与完整报告校验的差别，再对照现有类型、解析器和测试。独立教学代码只解释局部概念，不能替换业务模块；没有要求重复实现已有功能。

## 1. 非空文本检查之后，Judge 还需要哪些检查

打开 [workflow.py](../review_system/workflow.py)，找到：

```python
# 阅读片段：content 已由异步模型调用取得，省略外围状态与错误处理。
if not isinstance(content, str) or not content.strip():
    raise LLMError("The model returned empty or non-text content.")
if agent is JUDGE:
    final_review = parse_final_review(content, request.original_input)
```

仅非空文本检查能拒绝空白、`None` 和非字符串，却会接受下面三种内容；现有 Judge 解析器会进一步将它们拒绝：

```text
方案完全正确。
{"verdict": "banana"}
{"summary": "看起来可行，但还没有检查证据。"}
```

它们都是非空字符串，却不符合最终报告契约。现有程序还会检查字段、结论枚举、摘录位置与跨字段规则。

数据契约就是程序可执行的约定：哪些输入可接受、模型应返回什么、哪些情况失败、失败后保留什么。Analyst、Critic 保持非空文本输出，Judge 执行完整报告校验。

## 2. 四层检查，回答四个不同的问题

| 层次 | 检查的问题 | 能抓住的例子 | 仍不能证明的事情 |
| --- | --- | --- | --- |
| 文本检查 | 返回值是否为非空字符串？ | 空白、`None` | 内容是否符合格式 |
| JSON 解析 | 文本是否能按约定解析？ | 缺引号、附加说明、代码围栏 | 字段是否齐全、类型是否正确 |
| 契约校验 | 字段、枚举、位置、关系是否满足规则？ | 非法结论、错引原文、互相冲突的字段 | 推理和事实是否可靠 |
| 内容评估 | 结论是否被材料与可靠证据支持？ | 原文被引用了，但解释不成立 | 未提供的外部事实 |

例如，`{"verdict": "banana"}` 可以是合法 JSON，但不是合法审核结论。反过来，即使所有字段都合法，模型也可能错误理解一个正确引用的句子。

因此，结构化输出让错误更容易发现、结果更容易消费；它不会自动让模型变得正确。

### dataclass、类型标注与校验函数

`@dataclass` 帮我们保存字段、生成构造方法等重复代码。`verdict: str` 主要表达类型意图，不会自动限制为三个允许的取值。

`frozen=True` 限制字段重新赋值，也不会自动检查字段内容或递归冻结嵌套列表。现有契约模块使用 dataclass 保存通过验证的数据，用显式纯函数完成运行时检查。

这里的 Schema 指字段与规则的定义，不要求实现完整 JSON Schema 标准。HTTP 层另用 Pydantic DTO；纯业务契约仍可独立校验。

## 3. 契约 v1：请求、问题与最终报告

以下是现有业务契约 v1。提示词、校验器与测试必须遵守同一规则；HTTP 请求还包含 request_id，详见第四日材料。

### 3.1 ReviewRequest：原始材料与审核模式

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `original_input` | 字符串 | 非空白，长度 1–20,000；保存原样，不裁剪换行或空白 |
| `review_mode` | 字符串枚举 | `logic` 或 `evidence`，调用入口默认 `logic` |

`logic` 关注假设、因果、矛盾、推导与遗漏条件。`evidence` 关注输入中主张与所给依据的匹配程度，指出证据不足。

输入没有提供外部资料时，evidence 模式应写明限制。模式名称不会自动触发网页搜索或供应商事实核验。两种模式都允许报告 `logic` 和 `evidence` 类问题，模式决定关注重点，不把另一类问题强行隐藏。

### 3.2 Finding：能定位到原文的问题

每个 Finding 表示一项可以定位到原文的审核发现。

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `category` | 字符串枚举 | `logic` 或 `evidence` |
| `severity` | 字符串枚举 | `low`、`medium`、`high` |
| `message` | 字符串 | 非空白，解释问题与理由 |
| `suggestion` | 字符串 | 非空白，给出具体修改或验证行动 |
| `start` | 整数 | 原文中的起始位置，从 0 开始；拒绝布尔值 |
| `end` | 整数 | 结束位置，不包含该位置字符；拒绝布尔值 |
| `quote` | 字符串 | 非空白，必须等于原文切片 `original_input[start:end]` |

位置还需满足 `0 <= start < end <= len(original_input)`。所有字段必填；未知字段拒绝；不把 `"3"` 自动变成数字 3，也不把非法枚举自动纠正成相近值。

关于严重程度：`high` 表示足以影响核心结论或关键承诺的问题；`medium` 表示需要修正的重要缺口；`low` 表示局部改进。校验器只检查取值是否合法，实际分级是否恰当仍需内容评估。

如果问题是“缺少验证依据”，可以引用对应的原文主张。无法定位到具体主张的整体限制放到报告的 `limitations`，不要编造一句原文作引文。

### 3.3 FinalReview：通过校验的最终报告

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `summary` | 字符串 | 非空白，概括判断与主要理由 |
| `verdict` | 字符串枚举 | `pass`、`needs_revision`、`insufficient_evidence` |
| `findings` | JSON 中为列表，业务对象中为元组 | 可为空，每项完整验证 |
| `limitations` | JSON 中为字符串列表，业务对象中为元组 | 可为空，每一项非空白 |

同样要求全部字段出现，拒绝未知字段。额外执行三个跨字段规则：

1. `needs_revision` 必须至少有一条 Finding，说明需要改什么。
2. `pass` 不能同时包含 `high` 严重程度的问题。
3. `insufficient_evidence` 必须至少有一条 limitation，说明缺什么信息。

`pass` 的含义是“在本次材料和审核范围内可接受”，不表示所有现实条件已经验证。它可以包含低或中等程度的改进建议；如果这些问题已经妨碍接受方案，模型应选择 `needs_revision`。这种判断不能仅靠枚举校验解决。

### 3.4 一份完整的教学报告

给定原文：

```text
仅用内存保存记录，重启后历史仍在。
```

下面是人工编写的合法结构样例，不是模型生成结果：

```json
{
  "summary": "原文的历史保留承诺缺少持久化或恢复机制支持。",
  "verdict": "needs_revision",
  "findings": [
    {
      "category": "logic",
      "severity": "high",
      "message": "仅在进程内存中保存记录，不能支持重启后仍保留历史的承诺。",
      "suggestion": "将承诺改为当前运行期间保存；需要历史恢复时另行设计和验证存储机制。",
      "start": 9,
      "end": 16,
      "quote": "重启后历史仍在"
    }
  ],
  "limitations": ["仅评估了输入文字，没有运行实际服务或检查存储实现。"]
}
```

先检查字段是否齐全，再核对 `original_input[9:16]`。若把 `start` 改成 8，JSON 仍合法，但摘录不匹配，必须拒绝。

## 4. 引用定位为什么容易错

原文的位置必须建立在同一个未改写的字符串上。先去空格、替换换行、再套用旧位置，会把正确引用变成错误引用。

本设计使用 Python 字符串切片的位置，按 Unicode 码点索引；不是 UTF-8 字节位置，也不保证等于屏幕上的视觉字符数。当前 UI 直接使用已验证的 `quote` 展示，不需要另一套前端坐标计算。

不要先查找 `quote` 再自动替模型修正位置。原文可能包含两次相同文字，擅自选第一次会掩盖模型定位错误。这里选择严格拒绝，由后续独立任务考虑是否需要修复流程。

还有一个 Python 细节：布尔值属于整数类型体系，`isinstance(True, int)` 会得到真。因此对 JSON 位置字段可使用 `type(value) is int`，明确拒绝 `true` / `false`。

下面的独立教学程序只验证引用，不是完整的报告校验器。在项目根目录执行，不需要 API Key：

```bash
.venv/bin/python - <<'PY'
def validate_quote(original, finding):
    start, end, quote = finding["start"], finding["end"], finding["quote"]
    if type(start) is not int or type(end) is not int:
        raise ValueError("位置必须为整数，不能为布尔值")
    if not 0 <= start < end <= len(original):
        raise ValueError("引用范围不合法")
    if not isinstance(quote, str) or not quote.strip():
        raise ValueError("摘录必须为非空白字符串")
    if original[start:end] != quote:
        raise ValueError("摘录与原文位置不匹配")

original = "仅用内存保存记录，重启后历史仍在。"
good = {"start": 9, "end": 16, "quote": "重启后历史仍在"}
validate_quote(original, good)
print("合法引用：通过")

for label, change in [
    ("位置偏移", {"start": 8}),
    ("布尔值位置", {"start": True}),
    ("越界", {"end": 99}),
    ("伪造摘录", {"quote": "已经持久化"}),
]:
    try:
        validate_quote(original, {**good, **change})
    except ValueError as exc:
        print(f"{label}：已拒绝（{exc}）")
    else:
        raise AssertionError(f"应拒绝：{label}")
PY
```

这段程序的前提是已经拿到所需字段。完整解析器还必须先验证输入对象、字段集合与所有嵌套结构，不能把这个小函数当作整个契约层。

## 5. 模型被要求返回 JSON，程序还要检查什么

Judge 的提示词需要包含职责、字段与枚举、完整样例、原文引用规则，以及材料不足时如何表达不确定性。提示词中的要求是模型的目标；客户端收到的文本仍然需要程序检查。

现有 `parse_final_review` 的解析顺序：

```text
原始 Judge 字符串
  → 严格 JSON 解析
  → 顶层必须为对象，检查必填与未知字段
  → 检查每个字段的类型、空白和枚举
  → 遍历 findings，检查引用位置与摘录
  → 检查 verdict 与 findings / limitations 的关系
  → 构造 FinalReview
```

本设计不剥离代码围栏、不从大段文字中截取第一对大括号，也不在失败后自动补问模型。这样非法输出有确定的错误结果，测试也能检查调用次数。

标准库 `json.loads` 的默认行为还需要收紧：它默认接受 `NaN` 等非标准常量，遇到同名字段时保留最后一个值。现有解析器通过 `parse_constant` 拒绝非标准常量，通过 `object_pairs_hook` 检查重复字段名。这些检查适用于嵌套对象。

以下独立示例展示两个入口参数的作用，仍不包含报告字段校验：

```python
import json

def reject_constant(value):
    raise ValueError(f"不允许的 JSON 常量：{value}")

def unique_object(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError(f"重复字段：{key}")
        result[key] = value
    return result

def strict_loads(text):
    return json.loads(
        text,
        parse_constant=reject_constant,
        object_pairs_hook=unique_object,
    )

assert strict_loads('{"verdict":"pass"}') == {"verdict": "pass"}
for text in ['{"verdict":"pass","verdict":"needs_revision"}', '{"x":NaN}']:
    try:
        strict_loads(text)
    except ValueError:
        print("已拒绝：", text)
    else:
        raise AssertionError("应当拒绝")
```

注意，示例中只有 `verdict` 的对象通过的是 JSON 解析，完整报告校验仍应因缺字段而拒绝它。

客户端层继续负责网络错误和供应商响应外壳；契约层负责回答内容的规则；工作流层负责把契约失败附上阶段信息并停止流程。让三个层各承担明确的职责，测试时才能精确找到失败位置。

## 6. 阶段状态由程序记录

模型可能在输出中自称“审核已完成”，但程序才知道网络请求、校验和展示是否全部成功。状态不应由模型填写。

现有 `StageRecord`（包含 D3 扩展）：

| 字段 | 含义 |
| --- | --- |
| `agent`、`model` | 当前阶段角色与实际配置的模型 |
| `status` | `pending` / `running` / `succeeded` / `failed` / `skipped` / `cancelled` |
| `raw_output` | 模型返回的原始文本；没有拿到文本时为 `None` |
| `error_code` | `model_error` / `invalid_output` / `callback_error` / `network_timeout` / `model_timeout` / `total_timeout` / `cancelled`；无错误为 `None` |

现有 `ReviewRecord` 保存 `request`、有序的三个 `stages`、`final_review`、审核级 `status` 和 `error_code`。审核级状态为 `queued / running / succeeded / failed / cancelled`。只有整个流程成功才发布报告，失败或取消时为 `None`。记录在内存中，不是数据库历史；当前服务的任务管理和事件耗时由独立模块负责。

正常状态变化：

```text
pending → running → succeeded
                  ↘ failed
pending → skipped（前序阶段失败后，不再执行）
```

`succeeded` 表示阶段输出通过校验、可选内核回调执行成功，且期限检查通过。当前 UI 经 HTTP 在审核结束后展示，没有把页面渲染函数传给内核；下表的回调均指 Python 调用方提供的 on_response。

回调发生前，已验证的回答依旧会进入 `completed`，沿用 D1 行为。因此 `completed` 保存的是“已经取得的有效回答”，不能机械地认为其数量等于状态为 succeeded 的阶段数。

| 场景 | 状态：A / C / J | `completed` | `final_review` |
| --- | --- | --- | --- |
| 全部成功 | succeeded / succeeded / succeeded | A、C、J | 合法报告 |
| Critic 网络失败 | succeeded / failed / skipped | A | `None` |
| Critic 回调失败 | succeeded / failed / skipped | A、C | `None` |
| Judge 契约失败 | succeeded / succeeded / failed | A、C | `None` |
| Judge 回调失败 | succeeded / succeeded / failed | A、C、J | `None` |

Judge 契约失败时，它的 `raw_output` 可以留在失败阶段记录中，便于定位问题；它不是已接受的报告，也不能加入 `completed`。展示这段文本时应注明未通过校验。

输入校验失败发生在阶段运行前，直接拒绝，不启动模型。异步取消经 CancelledError 传播，使用 ReviewRun 查看最后快照，详见第三日材料；这与强制终止进程不同，不能保证任意中断后的恢复。

## 7. 现有契约怎样接入工作流与页面

当前业务内核为 run_review_async，在入口构造请求对象，review_mode 默认 logic；run_review 是给同步脚本的薄封装，客户端仍需提供异步 complete。

三阶段上下文始终携带 `review_mode`：Analyst 读原文与模式；Critic 还读 Analyst 文本；Judge 还读 Critic 文本。JSON 序列化继续使用原始输入，不为了引用定位而改写内容。

Analyst 与 Critic 在 v1 中保持文本输出。Judge 的 JSON 由 `parse_final_review` 校验；客户端 `complete()` 仍返回字符串，无需把业务契约放进 HTTP 客户端。

成功结果通过 record 暴露请求、阶段和报告，角色回答在 responses；WorkflowError 通过 record 与 completed 暴露失败快照。final_response 返回 Judge 原始 JSON 文本，结构化消费使用 record.final_review。API 将公开字段构造成 DTO，UI 核验完整响应后保存和展示；页面展示失败可在当前会话重跑恢复。

现有成功测试已经使用合法 Judge JSON，并断言模式键与前序输出。自行写练习时也必须满足这些条件；不要拿早期只返回字面字符串 J 的示例覆盖当前测试。

## 8. 如何用现有测试验证契约

对照 [test_workflow.py](../tests/test_workflow.py)，观察现有测试如何检查调用次数、上下文、部分结果与回调。同时阅读 [test_contracts.py](../tests/test_contracts.py) 的纯契约测试。

一个有效的失败测试至少回答三个问题：喂入什么坏数据；应出现什么错误；是否留下错误的成功结果。

例如“Judge 引用位置错误”的测试应检查：总调用数 3；错误阶段是 Judge；错误码为 `invalid_output`；前两份有效回答保留；Judge 状态为失败；`final_review` 为 `None`。只检查抛异常，会漏掉错误报告被保存的风险。

请求非法时应检查调用次数为 0。回调失败时应继续检查当前有效回答被保留。合法报告时应检查报告字段的实际值，而不只是“函数没有报错”。

纯函数校验测试不用联网。工作流测试用可控客户端返回预置 JSON；UI 测试使用既有的离线方式。测试通过证明程序遵守契约；真实模型能否持续生成合法报告、结论质量如何，要用另行记录的 live 样例评估。

### 参考答案

4. 因为布尔值会被当作整数类型实例。此处要求真实整数，可以用 `type(value) is int`。

10. 先用合法报告完成一次审核，再让下一次 Judge 返回非法引用；检查新错误、前序部分结果及失败状态，确认上次最终报告已清除，重跑页面也不会恢复旧报告或重复调用模型。

## 1. 多智能体在这个项目中是什么

这里的 Agent 是带有名称和独立系统提示词的角色对象。程序依次调用模型，让它以不同职责阅读材料。

```text
原始输入
  → Analyst：理解目标、假设、优点与问题
  → Critic：重读原文，检查 Analyst 的分析
  → Judge：阅读原文和前两份回答，形成最终结论
```

角色定义见 [agents.py](../review_system/agents.py)。角色决定这次调用做什么，模型决定由哪个模型执行。三个角色可使用同一模型，也可分别配置模型名。当前 live 服务使用一份供应商配置，各审核共享服务生命周期内的模型客户端；没有每角色独立供应商和 Key 的配置。

例如，输入声称：“用内存字典保存记录，所以服务重启后历史还在。”Analyst 应识别保存历史的目标与假设；Critic 应指出普通进程内存不能自动跨重启保留；Judge 应评估依据并给出修改建议。这是对角色职责的说明，不是实际模型结果。

Critic 需要原文，因为 Analyst 可能遗漏或误读；Judge 需要全部材料，以评估双方分歧。三个角色也可能共享偏差，三次调用并不自动保证审核准确。

提示词要求把材料中的嵌入指令当作待审核内容，但这不构成抵御所有提示注入的证明。`logic` 与 `evidence` 都只评估所给材料，当前没有联网核验或 RAG 检索。

**停下来想一想：**如果 Critic 只看到 Analyst 的摘要，会失去哪一种检查能力？

## 2. 找到每项工作的负责人

今天重点读角色、工作流和页面，其余先掌握职责；第二至第四日再分别深入契约、异步和服务。

| 文件 | 负责的事情 | 要定位的名称 |
| --- | --- | --- |
| [app.py](../app.py) | 输入、提交、保存会话结果和展示 | `submit_review`、`display_response`、`display_record`、`st.session_state` |
| [api_client.py](../review_system/api_client.py) | UI 向本地 API 发 HTTP 请求并核验响应 | `APISettings`、`ReviewAPIClient`、`APIClientError` |
| [api.py](../review_system/api.py) | 应用资源生命周期、路由、HTTP 错误映射 | `create_app`、`default_resources`、`error_response` |
| [service.py](../review_system/service.py) | 容量、执行中的标识与任务管理 | `ReviewService.review`、`aclose` |
| [agents.py](../review_system/agents.py) | 三个角色及独立提示词 | `ANALYST`、`CRITIC`、`JUDGE` |
| [workflow.py](../review_system/workflow.py) | 顺序、上下文、期限、结果与失败传播 | `run_review_async`、`ReviewRun`、`WorkflowError` |
| [contracts.py](../review_system/contracts.py) | 输入、Judge 报告、原文引用和阶段记录 | `validate_review_request`、`parse_final_review`、`ReviewRecord` |
| [clients.py](../review_system/clients.py) | 供应商 HTTP 请求与模型错误转换 | `AsyncLLMClient`、`AsyncOpenAICompatibleClient`、`LLMError` |
| [config.py](../review_system/config.py) | 供应商、模型与预算配置 | `Settings.from_env` |
| [environment.py](../review_system/environment.py) | 加载项目根目录的 `.env` | `load_project_env` |

一次正常页面提交的路径：

```text
app.py：点击 Review，检查输入，读取 APISettings，生成或复用 request_id
  → submit_review → ReviewAPIClient：POST /api/v1/reviews
  → FastAPI：检查请求，await ReviewService.review(...)
  → Service：检查重复标识与容量，生成 review_id，调用 run_review_async
  → 工作流：依次 await Analyst、Critic、Judge，校验 Judge 报告
  → API：返回成功或失败响应（可带部分结果）
  → UI 客户端：核验响应
  → app.py：保存会话结果，再展示所有有效回答、状态与报告
```

live 模式在服务启动时读取模型配置并创建共享 HTTP 客户端；fake 模式使用显式演示客户端。UI 不读取模型 Key，也不直接请求供应商。页面等待一次 HTTP 请求结束后统一展示，当前没有逐阶段推送或停止按钮。

模型调用与工作流通过 `AsyncLLMClient` 协议分开：

```python
async def complete(self, *, model: str, messages: list[dict[str, str]]) -> str:
    ...
```

工作流等待这个方法返回文本，不依赖某种 HTTP 库。live 传入真实模型客户端，测试传入异步替身，执行同一份业务内核。`Protocol` 的类型标注帮助表达约定，实际返回内容仍需运行时校验。

Python 教学脚本可调用同步薄封装 `run_review(...)`，它用 `asyncio.run` 执行异步内核，传入的客户端仍需异步 `complete`。已有事件循环时直接 `await run_review_async(...)`。`runtime.py` 提供管理单次脚本资源的入口；`OpenAICompatibleClient` 同步类保留供 HTTP 教学使用，均不是当前页面提交路径。

## 3. 手工追踪一次成功审核

用 `U` 表示原文，`A`、`C` 表示前两次调用的非空文本，`J` 表示符合契约的 Judge JSON 文本。`J` 不是字面字符串 `"J"`，这些符号都不代表真实模型审核结果。

### 3.1 先检查输入

业务内核通过 `validate_review_request(user_input, review_mode)` 校验输入：必须是非空白字符串，最多 20,000 个 Python 字符，模式为 `logic` 或 `evidence`。非法输入抛出 `ContractError`（属于 `ValueError`），模型调用为 0。

空白检查不裁剪合法原文；上限包含恰好 20,000 字符，与模型 token 数不同。UI、API、服务和内核分别在自身边界校验，HTTP 请求还有 `request_id` 和未知字段检查。

### 3.2 状态分别给谁使用

```python
completed: list[AgentResponse] = []
context = {"original_input": request.original_input, "review_mode": request.review_mode}
```

`completed` 保存已取得的有效角色回答，供返回与错误恢复使用；`context` 给下一阶段模型阅读。`AgentResponse` 有 `agent`、`model`、`content` 三个字段，它保存数据，不请求模型。

另外，`ReviewRecord` 保存请求、三阶段记录、审核状态、错误码与最终报告。`StageRecord` 包含角色、模型、状态、原始输出和错误码。`ReviewRun` 是调用方可保留的运行句柄，取消后仍能查看快照。

### 3.3 每次请求有两条消息

工作流构造消息的源码：

```python
messages = [
    {"role": "system", "content": agent.system_prompt},
    {"role": "user", "content": json.dumps(context, ensure_ascii=False)},
]
```

第一条说明角色职责，第二条把上下文编码为 JSON 文本。`ensure_ascii=False` 保留可读中文。调用经过 `_model_call(...)`，由它在单次模型预算内 `await client.complete(...)`。

live 客户端通过 HTTPX 发送 `/chat/completions` 请求，包含模型名、消息和 `stream=False`，从 `choices[0].message.content` 提取非空文本。一次正常审核调用三次模型，没有第四次汇总调用。

### 3.4 三轮上下文的变化

| 即将调用的角色 | `context` 的键 | 接受本阶段输出后 `completed` 的内容 |
| --- | --- | --- |
| Analyst | `original_input`、`review_mode` | Analyst：A |
| Critic | 上述两项，加 `analyst_output` | Analyst：A；Critic：C |
| Judge | 再加 `critic_output` | Analyst：A；Critic：C；Judge：J |

每次有效输出被接受后执行：

```python
response = AgentResponse(agent.name, model, content)
completed.append(response)
context[f"{agent.name.lower()}_output"] = content
```

每次请求生成自己的 JSON 字符串，后续字典变化不会改写已经发送的消息。Judge 成功后也写入 `judge_output`，但没有第四个角色读取。

### 3.5 原始回答、报告与展示

Analyst 和 Critic 的输出检查为非空文本。Judge 必须通过 `parse_final_review`：JSON、精确字段、类型、枚举、引用坐标和跨字段规则均合法后，才能加入有效回答。

引用要求 `quote == original_input[start:end]`，其中 `start` 为零基 Python 字符位置，`end` 不包含在引用中。这证明摘录与原文一致，不证明主张属实。

成功返回 `ReviewResult(tuple(completed), run.record)`。`result.final_response` 保留 Judge 的 JSON 文本；`result.record.final_review` 是程序可读的结构化报告，含摘要、结论、问题和限制。只有三个阶段及提供的回调都成功，才发布最终报告。

Python 调用者可提供 `on_response`，每取得一个有效回答就调用一次。当前 UI 没有向内核传展示回调，而是在完整 HTTP 响应收到并核验后展示结果；E05 脚本的逐阶段打印与页面行为不同。

UI 将本次结果保存到 Streamlit 会话；无新点击的页面重跑只恢复展示。新审核先清除旧结果和错误。服务没有数据库或历史查询；后端重启后没有恢复历史的机制，仍在页面会话中的已有结果也不能等同于持久化历史。

**停下来想一想：**Judge JSON 语法正确但引用错误，能否得到成功报告？

## 4. 失败时，系统怎样结束

### 4.1 模型失败和报告失败

Analyst 成功而 Critic 模型失败时，工作流抛出 `WorkflowError`，`agent` 为 `Critic`，`completed` 只有 Analyst，阶段为 `succeeded / failed / skipped`。Judge 不启动，最终报告为空。客户端与工作流处理网络、模型预算等错误，不添加自动重试或默认结论。

若 Judge 返回非法报告，原始输出留在失败阶段的 `raw_output`，不加入有效回答，错误码为 `invalid_output`。页面将其标记为未通过校验。

API 路径中，Service 将工作流失败转成 `ServiceError`，API 构造 HTTP 错误响应，UI 接收 `FailureResponse` 后保存部分结果和错误。UI 不直接捕获内核的 `WorkflowError`。

### 4.2 内核回调失败与页面展示失败

| 场景 | 模型调用次数 | 有效回答 | 后续行为 |
| --- | --- | --- | --- |
| 直接调用内核时输入非法 | 0 | 无 | 不启动任何角色 |
| Analyst 模型失败 | 1 | 无 | Critic、Judge 跳过 |
| Critic 模型失败 | 2 | Analyst | Judge 跳过 |
| Critic 内核回调抛出普通异常 | 2 | Analyst、Critic | `callback_error`，Judge 跳过 |
| Judge 模型失败或报告非法 | 3 | Analyst、Critic | 最终报告为空 |
| 三阶段及回调成功 | 3 | 三个角色 | 发布有效报告 |

内核先记录有效回答，再调用 `on_response`。所以 Critic 回调失败仍保留 Critic 回答，但阶段为 `failed`；`completed` 数量不一定等于成功阶段数。

当前页面在服务返回后才展示。如果页面渲染异常，已收到的结果保留在会话，可重跑恢复；这不会倒过来停止已经完成的服务端审核。页面渲染失败与内核 `callback_error` 是两条路径。

### 4.3 配置与服务连接错误

`load_project_env()` 加载固定的项目 `.env`；已有环境变量优先，包括值为空的变量。live 后端启动时读取 `Settings.from_env()`，缺 Key 等错误会阻止启动，绝不自动切为 fake。显式 fake 后端不需要模型凭据。

UI 读取自己的 `APISettings`，验证输入与配置后才发 HTTP 请求。服务未运行或 UI 等待超时，会得到 `APIClientError`；请求结果未确认时保留标识，不自动重试。标识只防止执行中的重复请求，完成后再次提交仍可能重新调用模型。

### 4.4 三种后端预算与 UI 等待

| 配置 | 默认值 | 约束范围 |
| --- | --- | --- |
| `REVIEW_TIMEOUT_SECONDS` | 60 秒 | HTTPX connect/read/write/pool 网络操作 |
| `REVIEW_MODEL_TIMEOUT_SECONDS` | 60 秒 | 一次模型调用的预算 |
| `REVIEW_TOTAL_TIMEOUT_SECONDS` | 150 秒 | 整次审核的预算，角色间不重置；直接调用内核排队时也计时 |
| `REVIEW_API_TIMEOUT_SECONDS` | 总预算加 30 秒 | UI 的 HTTP 操作等待，配置时需大于后端总预算 |

错误码分别为 `network_timeout`、`model_timeout`、`total_timeout`。HTTP 服务满载立即拒绝，不进入内核排队。总预算不包含上传和响应网络传输，也不是强制打断所有阻塞代码的硬期限。

任务取消会保留已完成结果并释放资源，随后继续传播 `CancelledError`。本地取消或超时不能证明供应商停止处理或计费；当前页面没有停止按钮，也不承诺网络断开必然取消审核。

### 参考答案

1. 不必须；独立提示词区分角色，模型名可覆盖，当前供应商和 Key 共用一份配置。
2. `original_input`、`review_mode`；再加 `analyst_output`；再加 `critic_output`。顺序由 `run_review_async` 的循环决定。

6. 内核回调失败保留 Analyst、Critic，但停止 Judge；页面渲染发生在服务响应之后，结果已保存，可重跑恢复。
7. 前者拒绝且不调用模型，后者可继续；空白检查不裁剪合法原文。
8. 无新点击的重跑恢复当前会话结果；没有持久化历史查询或恢复。
9. 分别约束网络操作、单次模型调用和整次审核，错误码不同；本地超时不能证明供应商停止。
10. 不能；还需真实调用的连通性、实际样例的质量、耗时与费用证据。

## Q02：标注一份请求

这是一份简化示意，省略自动生成的部分字段：

```http
POST /v1/chat/completions HTTP/1.1
Host: example.invalid
Content-Type: application/json
Authorization: Bearer synthetic-key

{"model":"fake-a","messages":[{"role":"system","content":"你是审查员"}],"stream":false}
```

1. 标出请求方法、目标路径和协议版本。
2. 列出请求头和请求体的边界。
3. `Content-Type` 和 `Authorization` 各负责什么？
4. `role="system"` 属于请求头还是请求体？
5. `model/messages/stream` 是 HTTP 强制规定的字段吗？

<details>
<summary>核对本题答案</summary>

1. 方法 POST；路径 `/v1/chat/completions`；版本 HTTP/1.1。
2. `Host`、`Content-Type`、`Authorization` 是请求头，空行之后的 JSON 是正文。
3. `Content-Type` 声明正文格式；`Authorization` 携带认证凭证。
4. `role="system"` 位于 JSON 正文的 `messages` 中，它是模型消息的角色字段。
5. 三个键是该模型接口的字段约定，HTTP 不强制要求这些名字。

</details>

## Q03：判断并解释

每题写出判断与理由。

1. 只要设置 `Content-Type: application/json`，就可以把 Python 字典原样放进这里的 `Request(data=...)`。
2. POST 的正文必须是 JSON。
3. `Authorization: Bearer ...` 会自动把 API Key 加密。
4. 设置 `stream=False` 后，这个网络调用就成为异步调用。
5. `Request(...)` 构造成功，说明服务端已经收到请求。

<details>
<summary>核对本题答案</summary>

1. `Content-Type` 只做声明。本题采用 JSON 字节正文，需要显式序列化与编码。
2. POST 不限定正文必须是 JSON；格式由接口约定。
3. Bearer 是认证方案，不是加密算法。HTTPS 负责传输保护。
4. `stream=False` 选择响应交付方式；当前调用仍同步等待。
5. `Request` 是请求描述对象；执行发送函数才发起网络操作。

</details>

## Q04：追踪字典、字符串和字节

先预测，再在 Python 中验证：

```python
import json

body = {"content": "中文", "stream": False}
text = json.dumps(body, ensure_ascii=False)
data = text.encode("utf-8")
restored = json.loads(data)
```

1. 分别写出 `body/text/data/restored` 的类型。
2. `text` 中的布尔值拼写是什么？
3. `restored == body` 的结果是什么？
4. `str(body).encode("utf-8")` 为什么不能可靠地替代前两次转换？
5. 默认 `json.dumps(body)` 中中文显示成 `\uXXXX`，解析后是否丢失中文？

<details>
<summary>核对本题答案</summary>

1. 依次为 `dict`、`str`、`bytes`、`dict`。
2. JSON 中是小写 `false`，解析回 Python 后是 `False`。
3. `True`。
4. `str(body)` 产生 Python 的字典表示，通常有单引号和 `False`，不符合 JSON 语法。编码只能把文本变成字节，不能修复格式。
5. 不会。`\uXXXX` 是 JSON 的转义表示，解析后恢复对应字符。

</details>

## Q06：修复一段请求构造代码

已知接口要求 POST、JSON 正文，并使用本项目的认证头策略：

<summary>核对本题答案</summary>

```python

    base_url + "/chat/completions",
```

完成 `complete_with_transport()`，复用 Q07、Q08。`send` 是必填的函数参数，作用相当于传入一个可替换的 `urlopen`，调用形式为：

```python
with send(request, timeout=settings.timeout_seconds) as response:
    ...
```

测试会传入 `Mock(return_value=BytesIO(...))` 模拟成功，或用 `Mock(side_effect=某个异常)` 模拟失败。

验收要求：

- 通过上下文管理器使用响应，成功、解析失败、读取中断时都退出上下文。
- 按下表转换网络异常，使用 `raise ... from exc`，保留 Q08 的 `LLMError`。
- 不重试、不返回空字符串冒充成功、不读取真实配置；`KeyboardInterrupt` 继续传播。

| 底层情况 | `LLMError` 的公开文字 |
| --- | --- |
| `HTTPError` | `Provider request failed (HTTP 状态码).`，例如 `Provider request failed (HTTP 401).` |
| `TimeoutError`，或 `URLError.reason` 是 `TimeoutError` | `Provider request timed out.` |
| 其他 `URLError` | `Could not connect to the model provider.` |
| 其他 `OSError` | `Provider connection failed while reading the response.` |
| `HTTPException` | `Provider connection was interrupted.` |

公开文字不包含底层异常中的 `synthetic-private` 合成内容。不要用 `except BaseException` 捕获所有退出信号。

超时分支还需传入 `LLMError(..., code="network_timeout")`，与异步模型客户端一致；其他分支保留默认的 `model_error`。这里的错误码描述本地调用结果，不表示供应商返回了某个 HTTP 状态码。

<details>
<summary>核对本题答案</summary>

完整代码见 `solution.py` 的 `complete_with_transport()`。

## Q11：检查超时承诺

有人说：“配置 `timeout_seconds=12`，所以三个角色合计一定在 36 秒内结束；超时就说明服务器返回了 504。既然失败了，直接再请求一次就行。”

指出三处不能直接成立的推论，3 分。再说明如果产品真的要求“整轮 36 秒内结束”，还需要定义什么，2 分。只写设计，不要求实现异步或整轮期限。

<details>
<summary>核对本题答案</summary>

三处问题：

- `urlopen` 的 timeout 面向网络阻塞操作，不等于每阶段的绝对总时限，不能直接乘三得出整轮上限。
- 本地超时不代表收到了 HTTP 504，也可能还没收到任何 HTTP 响应。
- 超时可能发生在服务已经接受请求之后。再次调用可能产生重复执行或费用；是否重试需要结合失败原因、服务约定和剩余预算决定。当前客户端没有自动重试。

如果要做整轮 36 秒期限，应定义统一开始时间与截止时间；把剩余预算传给阶段调用，并明确超时后如何停止或取消工作、关闭资源、保留已完成结果。调用方停止等待，也不能直接保证远端计算已停止。这里是设计要求，不是本练习已实现的能力。

timeout 的具体语义见 [Python urlopen 文档](https://docs.python.org/3.12/library/urllib.request.html#urllib.request.urlopen)。

</details>
